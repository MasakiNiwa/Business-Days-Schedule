# Business Days Schedule — 仕様書 v1.0 (draft)

営業日の概念を持ち、休祝日にかかった予定を自動で前営業日／翌営業日にずらして表示する、
**反復ルール駆動**のカレンダー。GitHub Pages で静的公開する。

---

## 1. 目的とスコープ

### 1.1 解きたい課題

実務のスケジュールは「日付」ではなく「**ルール**」で決まっている。

- 給与振込は「毎月25日。ただし土日祝なら**前**営業日」
- 社会保険料の納付は「毎月末日。ただし土日祝なら**翌**営業日」
- 請求書発行は「毎月**第5営業日**」
- 支払処理は「**月末2営業日前**」

一般的なカレンダーアプリはこの「営業日補正」を持たないため、毎月人間が手で日付をずらしている。
本アプリはその補正を自動化することだけに集中する。

### 1.2 スコープ内 (In Scope)

| # | 機能 |
|---|---|
| F-1 | 日本の祝日データを自動更新して取り込む |
| F-2 | 営業日カレンダー（土日・祝日・自社休業日・臨時営業日）の定義 |
| F-3 | 反復ルールの追加・編集・削除・有効／無効切替 |
| F-4 | 反復ルールの営業日補正（前倒し／後ろ倒し／補正なし／最近接） |
| F-5 | 月カレンダー表示・一覧表示 |
| F-6 | N営業日前の事前通知（準備日）表示 |
| F-7 | ルール定義の JSON エクスポート／インポート |

### 1.3 スコープ外 (Out of Scope) — 意図的に作らない

| # | 非目標 | 理由 |
|---|---|---|
| N-1 | **ルールを持たない単発予定の登録** | 汎用カレンダーの領域。既存アプリに任せる。本アプリの一貫性（＝すべての表示はルールから導出される）を守る |
| N-2 | サーバー・ログイン・複数ユーザー同期 | 静的ホスティングの範囲を出ない |
| N-3 | 通知メール・プッシュ通知 | 画面表示のみ |
| N-4 | 日本以外の祝日 | v1 では対象外（データ層は差し替え可能に設計する） |

> N-1 の例外として **「ルールの除外日」** は許可する（例: 毎月10日のルールだが 2026-08-10 だけ無し）。
> これは新しい単発予定の追加ではなく、既存ルールの例外指定であるため方針と矛盾しない。

### 1.4 想定利用者

個人（バックオフィス／経理／総務／個人事業主）。ブラウザ1台で完結する。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| **休業日** | 営業日カレンダー上、業務を行わない日。週末＋祝日＋自社休業日から臨時営業日を除いたもの |
| **営業日** | 休業日でない日 |
| **祝日** | 「国民の祝日に関する法律」に基づく祝日・振替休日・国民の休日 |
| **ルール (Rule)** | 反復条件・営業日補正・期間などをまとめた1件の定義 |
| **発生日 (Occurrence)** | ルールを展開して得られる1つの日付 |
| **基準日 (Raw Date)** | 営業日補正を適用する前の日付 |
| **確定日 (Effective Date)** | 営業日補正を適用した後の、実際に表示される日付 |

## 3. 祝日データ

### 3.1 データソースの決定

**一次ソースとして [`holiday-jp/holiday_jp`](https://github.com/holiday-jp/holiday_jp) の `holidays.yml` を採用する。**

| 項目 | 内容 |
|---|---|
| 取得 URL | `https://raw.githubusercontent.com/holiday-jp/holiday_jp/master/holidays.yml` |
| 収録範囲 | 1970-01-01 〜 2050-12-31（約1,330件。全期間をそのまま同梱する） |
| 文字コード | UTF-8 |
| 形式 | `2026-01-01: 元日` の1行1レコード（YAMLマップ） |
| 振替休日 | 収録済み（例: `2026-05-06: こどもの日 振替休日`） |
| 国民の休日 | 収録済み（例: `2026-09-22: 休日`） |
| 更新 | 内閣府の発表に追随してメンテナンスされている |

採用理由:
- UTF-8 の素直なテキストで、パースに外部ライブラリ・文字コード変換が不要
- 将来分（春分・秋分の計算値を含む）まで収録されており、来年以降のカレンダーが空にならない
- GitHub 上のファイルなので取得が安定し、コミット SHA で版を固定・追跡できる

> **注意（正確性の限界）**: 春分の日・秋分の日は前年2月の官報公示で正式確定する。
> それ以前の年の値、および将来の祝日法改正・臨時の祝日（改元・オリンピック等）は反映されていない可能性がある。
> UI 上に「◯年◯月◯日時点のデータ」と出典を明示する（§8.5）。

### 3.2 公開前の検査

holiday-jpのみをデータ源とし、内閣府CSVの取得・照合は行わない。
先にコミットSHAを取得し、その版のYAMLを取得する。データと出典の版を一致させる。
日付の実在・重複・名称・今年と翌年の件数と主要祝日の存在を検査し、
単体・ブラウザテストに成功した場合だけ公開する。

### 3.3 生成物: `src/data/holidays.json`

```jsonc
{
  "meta": {
    "source": "holiday-jp/holiday_jp",
    "sourceUrl": "https://raw.githubusercontent.com/holiday-jp/holiday_jp/<sha>/holidays.yml",
    "sourceSha": "a1b2c3d...",          // 取得時のコミット SHA
    "fetchedAt": "2026-09-07T07:29:23Z",
    "range": { "from": "1970-01-01", "to": "2050-12-31" },
    "count": 1329
  },
  "holidays": {
    "2026-01-01": "元日",
    "2026-01-12": "成人の日",
    "2026-05-06": "こどもの日 振替休日",
    "2026-09-22": "休日"
  }
}
```

- **収録するのは出典の全期間**（1970-01-01 〜 2050-12-31、1,329件）。年を絞れば
  同梱するファイルは小さくなるが、絞った外の年を開いたときに「収録範囲外」の
  警告が出てしまう。過去に遡って確かめたい場面があるため、全期間のまま持つ。
  48KB あるが gzip で約5KB であり、同梱の負担にはならない
- 日付キーは `YYYY-MM-DD` 昇順で安定ソートし、差分を読みやすく保つ
- `meta.range` は暦年の境界で切る。範囲末尾を最終祝日（11/23 など）にすると、
  その後の平日が「データ範囲外」と誤判定されてしまうため

### 3.4 更新と公開 `.github/workflows/deploy.yml`

- main の push、手動実行、毎週月曜 03:17 JST で実行する。
- 同じジョブで、SHA 固定の祝日取得 → データ検査 → 単体テスト → ビルド → E2E を実行し、Pages へ公開する。
- main へのコミット・push は行わない。`contents: read`, `pages: write`, `id-token: write` だけを使用する。
- **取得に失敗したときの扱いは、実行のきっかけで変える。**

  | きっかけ | 目的 | 取得できなかったとき |
  |---|---|---|
  | push / 手動 | コードの公開 | リポジトリの既存データで続行し、`::warning::` を残す |
  | 週次（schedule） | 祝日データの更新そのもの | 何も公開しない（`--require-fresh` で失敗させる） |

  **代替は「リポジトリの版」と「いま公開中の版」の新しいほう**を使う
  （`meta.fetchedAt` で比べる）。リポジトリの版だけに落とすと、週次更新で
  公開したぶんをリポジトリへ書き戻していないため、次の push で古い版へ
  巻き戻してしまう。しかも成功扱いなので、Actions が緑のままでは気づけない。

  いま公開中の版を読み戻せるよう、**ビルドは同梱データの写しを
  `dist/data/holidays.json` にも置く**。アプリは実行時にこれを読まない（§3.5）。
  置いてあるのは「いま公開されているのがどの版か」を次のデプロイへ伝えるためだけ。

  週次では代替を使わない。目的が祝日の更新そのものなので、更新できないなら
  公開する意味が無い。push のときは目的がコードの公開なので続行するが、
  黙って通さず警告として残す。どちらの代替も見つからないときは失敗させる。

  **公開中の版を確認できないときも代替を使わない。** 「読めなかった」と
  「まだ何も公開していない（404）」を分ける（`PublishedState`）。読めなかった
  ときにリポジトリの版へ落とすと、それが古ければ公開中のデータを巻き戻して
  しまう。ここで止めれば、いま公開されているものがそのまま残る（GitHub Pages は
  失敗したデプロイでは差し替わらない）。404 は巻き戻す先が無いので代替してよい。
  一時的な失敗で公開を止めないよう、諦める前に3回まで読み直す。
  判断は `chooseFallback()` に切り出してあり、ネットワーク無しで検査できる。
- API 呼び出しには `github.token` を渡す。認証なしの `api.github.com` は IP あたり
  60回/時で、共用ランナーではすぐ上限に当たる。トークンが無効なら一度だけ
  認証なしで試し直す（付けたせいで失敗させない）。
- **検査**に失敗した場合は公開を停止し、前回の Pages 成果物を維持する。
- リポジトリの JSON は開発用スナップショット。公開成果物の JSON は週次で新しくなる。
- 更新の監査には公開ページのフッターに出る `sourceSha` / `fetchedAt` と Actions の成功を使う。
  定刻の実行には遅延があり得る。

### 3.5 実行時は取りに行かない

**祝日データはビルドでアプリ本体へ同梱する。起動時に `fetch` しない。**

このデータは「配信中に中身が変わるもの」ではなく、デプロイのたびに作り直される
ビルド成果物である。JSON を別ファイルとして置いて起動時に取りに行っても、
中身は同じビルドの JS と必ず同じ版であり、得られるものが何も無い。
一方で費用は確実にかかる。JSON の URL は JS を解釈して初めて分かるため、
HTML → JS → JSON と直列に往復することになり、その間ずっと何も描けない。

低速回線を模した測定（遅延150ms・1.6Mbps、11回ずつ交互に実行）では、
取りに行く版は毎回 1,465〜1,476ms（中央値 1,468ms）だったのに対し、
同梱した版は 11回中5回が 1,020〜1,032ms まで下がり、残りは同水準だった。
速くなる場合の差はおよそ440ms（3往復ぶん）で、遅くなることは無い。
ばらつきの原因は測定側（手製の静的サーバーと使い捨てコンテナ）にあると見ており、
「必ずこれだけ速くなる」とは言えない。確かなのは、
**初回描画までに必要な往復が1つ減り、増えることはない**という点である。

同梱によって次のものが不要になった。

| 消えたもの | 理由 |
|---|---|
| `fetchHolidayData()` と実行時の検証 | 取得しないので、壊れた応答も届かない |
| 取得失敗時のエラー画面 | 失敗する経路が無い |
| Service Worker のデータ用分岐 | `/data/` を特別扱いする理由が無くなった |
| `startApp` の非同期化 | 待つものが無く、同期で描き切れる |

データの健全性はビルド時に担保する（§3.2）。実行時に検証しない代わりに、
`tests/holidaysData.test.ts` が同梱ファイル自体を CI で検査する。

## 4. 営業日カレンダー

### 4.1 定義

```ts
type BusinessCalendar = {
  id: string;                 // "company" | "bank" | 任意
  name: string;               // 表示名
  fiscalYearEndMonth?: Month; // 決算月（事業年度の終わる月）。未設定なら3月
  weekendDays: Weekday[];     // 既定 [0, 6]（日・土）。土曜出勤なら [0]
  useNationalHolidays: boolean; // 既定 true
  closedRanges: AnnualRange[];  // 毎年繰り返す休業期間（年末年始・夏季休業など）
  closedDates: DateStr[];       // 臨時休業日（単発）
  openDates: DateStr[];         // 休業日だが営業する日（祝日出勤など）
};

type AnnualRange = {
  from: "MM-DD";   // 例 "12-29"
  to:   "MM-DD";   // 例 "01-03"（年をまたぐ指定を許可）
  label: string;   // "年末年始休業"
};
```

`MM-DD` は**形だけでなく実在する月日**であること（`isValidMonthDay`）。`13-01` や
`02-30` を通すと、以後の営業日計算が例外で落ち、再読み込みしても同じところで
落ちて画面が戻らなくなる。3か所で受け止める。

1. 設定画面が入力を確定させない（該当欄の直下に理由を出す）
2. `validateCalendar` が取り込み時に弾く
3. `createBusinessDayCalendar` が読み込み時に取り除く。すでに壊れた値が
   保存されていても、その休業期間だけを無視して残りは動かす

### 4.2 判定ロジック（優先順位）

```
isBusinessDay(date):
  1. openDates に含まれる            → 営業日   (最優先)
  2. closedDates に含まれる          → 休業日
  3. closedRanges のいずれかに該当   → 休業日
  4. useNationalHolidays かつ祝日     → 休業日
  5. weekendDays に曜日が含まれる     → 休業日
  6. それ以外                        → 営業日
```

`openDates` を最優先にすることで「祝日だが出社」を無条件に表現できる。

### 4.3 プリセット

| ID | 名称 | 定義 |
|---|---|---|
| `company` | 自社カレンダー（既定） | 土日＋祝日。年末年始 12/29〜1/3 を既定で休業に設定 |
| `bank` | 銀行休業日 | 土日＋祝日＋12/31〜1/3 |

年末年始の休業日数は会社ごとに異なるため、`company` の 12/29〜1/3 はあくまで初期値であり、
設定画面から変更できる。

ルールごとに `calendarId` を指定できる。
「社内締めは自社カレンダー、振込は銀行カレンダー」といった使い分けが1画面で成立する。

## 5. スケジュールルールのデータモデル

### 5.1 Rule

```ts
type Rule = {
  id: string;                 // UUID v4
  title: string;              // 例 "給与振込"
  color: ColorToken;          // プリセット8色から選択
  group?: string;             // §5.6 グループ（空・未設定は「未分類」）
  note?: string;              // 備考（ツールチップに表示）
  enabled: boolean;           // 一時的に無効化できる
  calendarId: string;         // 参照する営業日カレンダー（既定 "company"）

  recurrence: Recurrence;     // §5.2
  adjust: Adjustment;         // §5.3
  notices: Notice[];          // §5.4（事前通知）

  period: { start: DateStr | null; end: DateStr | null };  // 有効期間（null は無期限）
  skipDates: DateStr[];       // 除外する【基準日】のリスト

  createdAt: string;
  updatedAt: string;
};

type Weekday = 0 | 1 | 2 | 3 | 4 | 5 | 6;   // 0=日曜
type Month   = 1 | 2 | ... | 12;
type DateStr = `${number}-${number}-${number}`;  // "YYYY-MM-DD"
```

### 5.2 Recurrence（反復条件）— 4種類

種類を絞りつつ、`months` フィルタと配列指定の組み合わせで実務パターンを網羅する。

#### (a) `weekly` — 毎週 / 隔週

```ts
{
  type: "weekly",
  interval: number,      // 1=毎週, 2=隔週, 4=4週ごと
  weekdays: Weekday[],   // 例 [1, 5] = 月曜と金曜
  anchor?: DateStr       // interval >= 2 のときの位相基準（省略時は period.start、それも無ければ 1970-01-05(月)）
}
```

#### (b) `monthlyByDay` — 毎月N日 / 月末

```ts
{
  type: "monthlyByDay",
  interval: number,              // 1=毎月, 3=3か月ごと
  months?: Month[],              // 対象月フィルタ。省略＝全月。例 [3,6,9,12] で四半期
  days: (number | "last")[],     // 例 [25] / [10, 25] / ["last"]
  overflow: "clamp" | "skip"     // 31日指定で2月など、存在しない日の扱い。既定 "clamp"
}
```

- `"last"` は月の暦上の末日（2月なら28/29日）
- `overflow: "clamp"` … 30日指定 → 2月は28/29日に丸める
- `overflow: "skip"` … その月は発生させない

> **編集画面では 31 と `"last"` を分けない。** 31日を指定した月はすべて末日であり、
> 2つ並べても選ぶ側が迷うだけになる。トグルは `31 / 末日` の1つにまとめ、内部表現は
> `"last"` に寄せる。以前の版が保存した `31` も同じトグルとして扱う。
> これにより `days` に 29・30 以外の「存在しない日」は入らなくなるため、
> `overflow` の設問は29日・30日を選んだときだけ出す（§8.4）。
- `months` を1つだけ指定すれば年次ルールになる（例: `months:[4], days:[1]` = 毎年4月1日）

#### (c) `monthlyByWeekday` — 毎月第N曜日

```ts
{
  type: "monthlyByWeekday",
  interval: number,
  months?: Month[],
  nth: (1 | 2 | 3 | 4 | 5 | -1)[],   // -1 = 最終。例 [2, 4] = 第2・第4
  weekday: Weekday
}
```

- 第5週が存在しない月は `nth: 5` を発生させない（`-1` を使えば最終週を確実に取れる）

#### (d) `monthlyByBusinessDay` — 毎月第N営業日 / 月末からN営業日前

```ts
{
  type: "monthlyByBusinessDay",
  interval: number,
  months?: Month[],
  nth: number[]      // 正 = 月初から数えてN営業日目（1 = 第1営業日）
                     // 負 = 月末から数えてN営業日目（-1 = 最終営業日, -3 = 月末3営業日前）
}
```

- 該当月の営業日数が `|nth|` 未満なら発生させない
- **このタイプは §5.3 の営業日補正を適用しない**（定義上すでに営業日であるため）

#### (e) `fiscalRelative` — 決算月を基準にした反復

```ts
{
  type: "fiscalRelative",
  offsetMonths: number[],   // 決算月からのずれ。0=決算月, 2=2か月後, -3=3か月前
  day: number | "last"      // ずらした先の月の何日か。存在しない日は末日に丸める
}
```

決算月の末日を基準に、`offsetMonths` か月ずらした月の `day` 日に発生する。

**この型が存在する理由**は、申告期限・期首・中間申告・四半期が「暦の何月」ではなく
「決算月から何か月」で決まるためである。暦月で書くと、決算月が変わったときに
すべてのルールを直して回ることになる。決算月を営業日カレンダーの設定に持たせ、
そこを基準にすることで、**設定を1つ変えるだけで関連する予定がまとめて追従する**。

| 実務 | 表現 |
|---|---|
| 法人税・消費税の申告（事業年度終了から2か月以内） | `offsetMonths:[2] day:"last"` |
| 期首 | `offsetMonths:[1] day:1` |
| 中間申告（開始から6か月経過後2か月以内） | `offsetMonths:[8] day:"last"` |
| 四半期末 | `offsetMonths:[-9,-6,-3,0] day:"last"` |

3月決算なら申告期限は5月末、12月決算なら翌年2月末になる。営業日補正（`next`）と
組み合わせれば、期限が休業日にあたったときの繰り下げも自動で効く。

決算月は**ルールが参照する営業日カレンダー**から取る。未設定のカレンダーでは
3月として扱う（日本で最も多いため）。

> **設計メモ**: 「毎年」「四半期」「毎営業日」を独立した型にしない。
> 年次は `monthlyByDay` + `months:[m]`、四半期は `months:[3,6,9,12]` で表現できる。
> UI 側では「年次」「四半期」というプリセットボタンを用意し、内部的には上記へ変換する（糖衣構文）。

### 5.3 Adjustment（営業日補正）

```ts
type Adjustment = {
  mode: "none" | "prev" | "next" | "nearest" | "both";
  keepInMonth: boolean;   // true のとき、補正が月をまたぐ場合は逆方向へ補正する。既定 false
};
```

| mode | 挙動 |
|---|---|
| `none` | 補正しない（休業日でもその日に表示） |
| `prev` | 休業日なら**遡って**最初の営業日へ（給与振込・締め処理） |
| `next` | 休業日なら**進んで**最初の営業日へ（納付期限） |
| `nearest` | 前後で近い方の営業日へ。**距離が同じなら `prev` を優先**（前倒しの方が実務上安全） |
| `both` | 前営業日と翌営業日の**両方**へ。1つの基準日から2件の発生日が生まれる |

`both` は、同じ期日に複数の相手が絡み、相手ごとに前倒し・後ろ倒しが分かれる場合のためにある。
たとえば他社からの入金が「5の倍数と月末」に集中し、休業日のときにどちらへずれるかが
取引先によって違うケース。1つのルールで両側を押さえ、カレンダー上は `←` `→` で区別する（§8.2）。
`keepInMonth` が true のときは、当月内に収まる側だけを残す。

`keepInMonth: true` の例:
- 2026年8月1日は土曜。`mode: "prev"` なら通常は7月31日（金）だが、月をまたぐため8月3日（月）へ補正
- 月次処理を当月内に収めたい場合に使う

補正の探索は最大 **31日** まで。それを超えても営業日が見つからない場合（設定ミスで全日休業など）は
その発生日を破棄し、UI に警告を表示する。

### 5.4 Notice（前後の予定 / 準備日・フォロー）

```ts
type Notice = {
  id?: string;          // 固定の識別子。外部カレンダーの UID に使う
  label: string;        // 例 "振込データ作成" / "入金の確認"
  timing?: NoticeTiming;  // 日付の決め方
  role?: NoticeRole;      // 前後が timing から決まらないときの意図
  offset?: number;        // @deprecated 旧形式。読み込み時に timing へ均す
  unit?: "business" | "calendar";  // @deprecated 同上
};

type NoticeTiming =
  // ① 日数で指定: 負 = 前（準備日）、正 = 後（フォロー）。0 は不可
  | { kind: "offset"; offset: number; unit: "business" | "calendar" }
  // ② 週と曜日で指定: 「翌週の水曜、休業日なら翌営業日へ」
  | { kind: "weekday"; weeks: number; weekday: Weekday; onClosed: "next" | "prev" | "none" }
  // ③ 月と第N営業日で指定: 「翌月の第5営業日」。nth が負なら月末から
  | { kind: "monthlyBusinessDay"; months: number; nth: number };

type NoticeRole = "before" | "after";
```

**日付の決め方（`timing`）は名称・識別子から独立させる。** 決め方を差し替えても
「同じ予定」でいられるようにするため。`id` と `label` は `timing` の外に置く。

**決め方を3通り持つ理由。** 日数だけでは実務の言い回しを写せない。
「翌週の水曜、水曜が休みなら木曜」は営業日でも暦日でも一定の日数にならない
（本体が週のどこにあるかで変わる）。「翌月の第5営業日」も同じで、本体からの
日数は月ごとに動く。日数へ言い換えさせると、設定した人の意図が消える。

- **② 週と曜日**: 週は**月曜始まり**（`WEEK_START = 1`）。本体の確定日が属する週を
  基準に `weeks` 週ずらし、その週の `weekday` を指す。日曜は前の週として数える
  （そうしないと日曜の本体から見た「翌週水曜」が9日先へ飛ぶ）。
  `onClosed` は指定曜日が休業日だったときの扱い。`next` は**翌営業日へ送る**
  （木曜も休みなら金曜以降）。「水曜が休みなら木曜」と固定するのではない
- **③ 月と第N営業日**: 本体の確定日の月を `months` ずらし、その月の第N営業日。
  `nth` が負なら月末から数える（`-1` が最終営業日）。その月の営業日数を超えたら
  日付を作らず、`notice-unresolved` の警告を出す（黙って消さない）

  画面では符号を出さず、繰り返し設定と同じ「月初から／月末から」＋営業日数に
  分ける。負数が要ることは読み上げ用のラベルにしか書けておらず、画面を見て
  いるだけでは気づけなかった

**編集中の状態はモデルと同じ形では持たない**（`TimingState`）。モデルは向きを
符号で表すが、画面は「大きさ」と「向き」を別々の欄に分けている。これを符号
ひとつに畳んで持つと情報が落ちる（`-0 < 0` は false、`-(-3)` は 3）。実際に
次の3つが起きた。

- 決め方を切り替えて戻すと、元の値ではなく既定値に戻る
- 日数に負の数を入れると、「前」を選んだまま後ろの日付で保存できる
- 欄を空にしたまま別の予定を追加すると、向きが入れ替わる

編集中は分けたまま持ち、保存する形へ畳むのは書き出すときだけにする
（`timingOfState`）。畳めない値（0 や負の大きさ）はモデルへ書かず、その予定の
欄の直下にエラーを出して保存を止める（`timingStateIssue`）。無理に畳むと
符号が反転し、画面と保存値が食い違う。

状態は**予定の id で覚える**。行を作り直しても消えないようにするため。
決め方ごとの値を3つとも持ち、**編集を始めた時点の値もここで登録する**
（登録しないと、切り替えて戻したときに「覚えていない」ことになり既定値へ落ちる）

**旧形式（`offset` / `unit` を直接持つ）は読み込み・取り込みの時点で `timing` へ均す。**
二重には持たない。既に保存されているデータは意味を変えずにそのまま移行する。

**`id` は配列の順番から独立させる。** 順番を UID に使っていたため、1件消すと
残りの識別子がずれ、**消したものの識別子を引き継いで**しまっていた。
取り込み先では、別の予定として増えたり、別の予定を上書きしたりする。

`id` を持たない古いデータには、読み込み・取り込みの時点で今の順番から
`n0`, `n1`, … を割り当てる。こうすると移行の時点では UID が変わらず、
そのあとの削除・並べ替えでも動かなくなる。

**前だけでなく後ろにも置ける。** 実務が「準備 → 本体 → 確認」の形をとることが
多いためである。請求書を出したら入金を確認し、振込を流したら結果を確かめる。
これを別々のルールとして作らせると、本体が営業日補正で動いたときに
片方だけ取り残される。

- 起点は**確定日**（補正後の日付）。本体が動けば前後の予定も一緒に動く
- `unit: "business"` の場合、休業日をスキップして数える
- 表示は本体ルールと視覚的に区別する（淡色・破線枠）
- `Occurrence.kind` は `notice`（前）と `follow`（後）に分かれる。
  同じ日に重なったときは 本体 → 準備日 → フォロー の順に並べる

**前後の別は、意図ではなく実際の日付で決める。** `date < main.date` なら `notice`、
そうでなければ `follow`。②で「翌週の月曜、休業日なら前営業日へ」と書くと、
休業日を避けた結果が本体を追い越して前へ戻ることがある。そのときは準備日として
並べたうえで `notice-role-mismatch` の警告を出す（日付は消さない）。

**日付を決められなかった前後予定は、保存ボタンのそばに常時出す。**
折りたたみ（「次の10回をすべて見る」）の中にしか出していなかったため、
畳んだままだと直近プレビューから関連予定が消えるだけで、気づかずに保存できた。
同じ理由が何か月ぶんも続くので件数にまとめ（「10 件の回で日付を決められません」）、
その回ごとの具体は折りたたみの中に置く（`PreviewSeries.unresolved` の
`reason` と `detail`）。

**書き出しの警告は、実際に書き出す予定と同じ条件で絞る。** 書き出すかどうかは
実際の日付（`Occurrence.kind`）で決まるので、設定上の向き（`noticeRole`）で
絞ると対象がずれる。休業日補正でフォローが本体より前へ移動すると、
「準備日だけ書き出す」で対象が出力されるのに警告が出ず、「フォローだけ書き出す」で
出力されないのに警告が出ていた。日付を作れた警告は `noticeKind`（実際の側）で、
作れなかった警告は `noticeRole` で絞る（実際の向きが無いため）。

**警告は結果ごとに分けて出す**（`exportWarningPrompt`）。3つは起きることが違う。
一括で「書き出されません」と言うと、実際には書き出される予定まで出ていないと
読ませてしまう。

| 種別 | 警告の理由 | 実際の結果 |
|---|---|---|
| 出ない | `notice-unresolved` / `no-business-day` | 書き出されません |
| 出るが別カレンダー | `unknown-calendar` | 書き出しますが、別のカレンダーで計算しています |
| 出るが要確認 | `notice-role-mismatch` | 書き出しますが、本体との前後が設定と逆になっています |

**警告の対象は表示範囲で絞る**（`expandRules`）。探索範囲は表示範囲に出る前後
予定を取りこぼさないために広げてあるので、そのまま返すと「3月を書き出したいのに
前年11月の話」が並ぶ。前後予定の警告は、その本体（`rawDate`）が表示範囲に
あるかで判断する。`rawDate` が `null` のもの（カレンダーが見つからない等、
ルール全体の話）は日付で絞れないので常に残す。

**外部カレンダーの UID には、実際の日付ではなく設定から決まる向きを使う**
（`Occurrence.noticeRole`）。`kind` は休業日の設定しだいで入れ替わる。
「翌週の月曜、休業日なら前営業日へ」は、月曜を休業日にした途端フォローから
準備日へ変わり、同じ予定の UID が変わってしまう（取り込み先では別の予定として
増える）。日数指定では符号がそのまま向きなので、これまで書き出したぶんと
同じ文字列になり、既存の UID は変わらない。

**設定が向きを言っていないものは、持ち主の意図をそのまま残す。** 編集画面が
保存のたびに役割を「後」で塗り替えていたため、「同じ週」「同じ月」の準備予定は
開いて保存するだけでフォローへ変わり、UID まで変わっていた（日付の設定を
触っていないのに別の予定として扱われる）。`TimingState.role` に意図を持ち、
ずらす数が 0 のときだけそれを使う。

**設定が向きを言っていないものは照合しない**（`declaredRoleOf` が `null` を返す）。
①は符号、②③は `weeks` / `months` の符号が向きを決めるが、`weeks: 0`（同じ週）と
`months: 0`（同じ月）だけは本体の位置しだいで前にも後にもなる。ここで既定の
「後」と突き合わせると、正しい設定に警告が出続ける。

**展開範囲は決め方ごとに広げる**（`expandBoundsFor`）。
既定のマージンは前後1か月しかないため、これが無いと本体が範囲外にあるぶんの
前後予定が黙って消える。

- ①は向きが決まるので片側だけ広げる。ただし**暦日の見積もりでは足りない**。
  「月曜だけ営業」のカレンダーでは60営業日が約420日になる。**そのルールの
  カレンダーを実際に歩いて**求める（`calendar.addBusinessDays`）。汎用の
  暦日換算だと、対象年だけ臨時休業が多いカレンダーで足りなくなり、年間の
  展開には出る準備日が月単位の展開では警告もなく消えていた
- ②③は前後どちらへも動きうるので、向きで分けず両側へ広げる
  （②は `|weeks| * 7 + 7` 日、③は `|months| + 1` か月）
- **前後予定ごとの必要量は足し合わせず、最も遠いものに合わせる**。同じ
  「30営業日前」を20件付けても必要な範囲は1件ぶんと変わらないのに、加算すると
  6年先まで探索して1回あたり1秒かかっていた。入力のたびにプレビューを計算する
  ため、そのまま操作の重さになる

### 5.6 グループ

実務では「税務」「入金」「社内」のように**束で見たい・束で渡したい**ことが多い。
ルールが増えるほど、全部を1つのカレンダーに重ねても読めなくなる。

**独立した実体にはせず、ルールが持つ文字列として扱う。** グループを実体にすると、
名前を変える・空になった束を片付ける・消えた束を参照しているルールを直す、といった
仕事が増える。文字列なら、名前を変えるだけで束ね直せる。

| 値 | 意味 |
|---|---|
| `"税務"` など | その名前の束に属する |
| `""` / 未設定 | 未分類。画面では「未分類」と呼ぶ |

- 比較の前に前後の空白を落とす。「税務」と「税務 」が別の束になると、絞り込みで片方が消える
- 選択中の束が消えた（名前を変えた・最後の1件を消した）ときは、その束だけを落とす。
  全部消えたら「すべて」へ戻す。何も出ない画面で固まらせないため
- 画面での絞り込みと書き出しは**同じ集合**を使う。片方だけ絞られていると、
  画面に出ていない予定が取り込み先へ紛れ込む
- 絞り込みが**1つだけ**のときに新しいルールを足すと、その束を初期値にする。
  何も指定せずに作ると、追加した直後に画面から消えて戸惑わせる。
  複数選んでいるときはどれに入れたいのか決まらないので、指定しない

**束は複数同時に選べる**（`activeGroups: string[] | null`）。「税務と入金だけを
見比べたい」という使い方が実際にあり、1つずつしか選べないと見比べるたびに
選び直すことになる。「すべて」から1つ押したらその束だけに絞る
（全部選んだ状態から1つ外す動きにすると、押した意図と逆になる）。
書き出しの対象も同じ形で選ぶ。保存済みの旧形式（1つだけの文字列）は
読み込み時に配列へ均す。

**まとめて扱う操作を用意する。** グループは実体ではなく文字列なので、
名前の付け替えは「その名前を持つルールを全部書き換える」ことになる。
1件ずつ編集させると取りこぼす。

| 操作 | 中身 |
|---|---|
| 名前を変更（`renameGroup`） | その束のルールの `group` をまとめて書き換える。空にすると未分類へ移す |
| まとめて削除 | その束のルールをすべて消す。件数を見せて確かめてから実行する（元に戻せない） |

**名前の長さは付け替えの時点で確かめる**（`GROUP_NAME_MAX`。読み込み側の
`LIMITS.groupLength` と必ず揃える。テストで固定してある）。読み込み側は上限を
超えるグループ名を持つルールを不正として捨てるため、検証せずに保存すると
**その束のルールが再読込で丸ごと消え**、さらにその状態で保存し直すと消えたまま
上書きされる。実際に41文字の名前で「支払」の2件が消える状態になっていた。

弾くときは1件も書き換えない。一部だけ変えると、同じ束が2つの名前に割れる。

一括操作は**1か所にまとめて畳む**。束の見出しごとにボタンを常時並べると、
予定を読むだけのときにも目に入り続ける。たまにしか使わない操作である。
- サンプルの束にはあらかじめグループを付ける（基本 / 税務 / 売上・入金 / 支払・振込 / 会議・報告）。
  使い始めた時点でグループが役に立つ状態にしておく

## 7. 展開アルゴリズム

### 7.1 全体フロー

```
expandRules(rules, calendars, holidays, viewRange) -> Occurrence[]

for each rule where enabled:
  1. 反復条件を viewRange（＋前後1か月のマージン）で展開 → 基準日リスト
  2. period.start / period.end で絞り込み
  3. skipDates に含まれる基準日を除外
  4. 各基準日に営業日補正を適用 → 確定日
     （monthlyByBusinessDay は補正をスキップ）
  5. 同一ルール内で確定日が重複したものを1件に統合
  6. notices を展開して副次的な Occurrence を生成
  7. viewRange 外を切り落とす
```

**マージンが必要な理由**: 月末の `prev` 補正で前月へ、月初の `next` 補正で翌月へ移動しうるため、
表示範囲の前後1か月を展開してから切り落とす。

### 7.2 Occurrence

```ts
type Occurrence = {
  ruleId: string;
  kind: "main" | "notice";
  rawDate: DateStr;        // 補正前の基準日
  date: DateStr;           // 補正後の確定日
  shifted: boolean;        // rawDate !== date
  shiftDirection: "prev" | "next" | null;
  noticeLabel?: string;
};
```

`shifted === true` の場合、UI に補正マーク（⟳）と元日付を表示する。

### 7.3 日付演算の実装方針（重要）

**タイムゾーンによるオフバイワンを構造的に防ぐ。**

- アプリの日付は常に `"YYYY-MM-DD"` 文字列で保持する
- 内部演算は `Date.UTC(y, m-1, d)` で生成した Date（＝UTC 00:00）で行い、
  取り出しは必ず `getUTCFullYear` / `getUTCMonth` / `getUTCDate` を使う
- `new Date("2026-01-01")` や `getDate()`（ローカル時刻系）は **使用禁止**。
  `tests/dateApiGuard.test.ts` が `src/` を走査して混入を検出する（`dateUtil.ts` のみ例外）。
  ESLint を導入していないのは、この1点のためだけに依存を増やす必要がないため
- 「今日」の判定のみ、`Asia/Tokyo` に固定して算出する（`Intl.DateTimeFormat` の `timeZone: "Asia/Tokyo"`）

## 8. UI 仕様

### 8.1 画面構成

```
┌──────────────────────────────────────────────────────────────┐
│ Business Days Schedule  反復ルールを組んで、…         v1.4.0 │
│ [今日]      [‹] 2026年9月 [›]   [カレンダー|一覧]            │
│                                 [ルール][書き出し] [◐][⚙][?] │
├──────────────────────────────────────────────────────────────┤
│ グループ [すべて ▾]                     表示 [内容|点]        │
│ 自社カレンダー: 営業日19日 / 休業日11日 ・ 決算月 3月 ⚙        │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                     月カレンダー（全幅）                       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**カレンダーは常に全幅**とし、それ以外の画面（ルール一覧・ルール編集・日付の詳細・
設定・ヘルプ）はすべて `<dialog>` のモーダルに載せる。

理由は2つ。
1. 横にパネルを置くとセル幅が削られ、予定名が折り返しやすくなる。カレンダーは
   1日の中身が読めることが最優先である
2. 1カラムに折り返す狭い画面では、パネルがカレンダーのはるか下に置かれて
   見つけにくかった。モーダルなら画面幅によらず同じ場所に出る

`<dialog>` を使うことで、Esc で閉じる・背面を操作させない・フォーカスを閉じ込める、
といった挙動をブラウザに任せられる。背景クリックでも閉じる。
なお `showModal()` は文書に接続済みの要素にしか使えないため、挿入してから開く。

ヘッダーは **左（今日）／中央（‹ 年月 ›）／右（操作）の3ゾーン**に分ける。
左右を同じ幅にすることで、年月がページ＝カレンダーの中央線に揃う。移動ボタンは
年月のすぐ両横に置き、視線の移動を小さくする。

右のボタンは順に、表示切替（カレンダー／一覧）、**日常の操作**（ルール一覧・書き出し）、
**たまにしか使わないもの**（配色モード ◐ 自動 / ☀ ライト / ☾ ダーク、設定 ⚙、ヘルプ ?）。
後ろ2組は見た目でも束ねて置く。並びが均一だと、どれが日常の操作なのか読み取れないため。
いずれもトグルで、同じボタンをもう一度押せば閉じる。

**書き出しはヘッダーに出す。** 設定の奥に置いていたが、反復ルールを組んで会社の
カレンダーへ持ち込むことがこのアプリの主目的であり（§1）、その出口を階層の下に
埋めると使い方そのものが伝わらない。

カレンダー・一覧のすぐ上に、**グループの絞り込みと予定の出し方**を置く。
どちらも「いま見ているものの見え方」を決める操作で、対象のすぐ上にあるほうが
結び付きが分かる。ヘッダーへ混ぜると、どれが対象への操作なのか読めなくなる。
グループの絞り込みは、グループが1つでも使われているときだけ出す。

カレンダーの真上に、**いま何が効いているか**（カレンダー名・営業日数・決算月）を
一行で出し、押すとその設定が開くようにする。決算月から逆算できること自体が
設定の中にしか現れず、機能があると気づかれなかった。効いているものを見せる場所は、
そのまま入口として使える。

**年月をクリックすると月の移動が開く**（§8.7）。前後1か月ずつの ‹ › だけでは
離れた月に届かないため。

**スマートフォンでは横スワイプで月を送る。** 左へ払うと次の月、右へ払うと前の月
（紙をめくる向きに合わせる）。縦スクロールを邪魔しないよう、横の移動量が縦の1.5倍を
超え、かつ60px以上動いたときだけ反応する。スワイプ直後のタップ扱いの click は
1回だけ握り潰す。そうしないと日付の詳細が同時に開いてしまう。

ルールが1件も無いときは、カレンダーの下に「サンプルを読み込む／ルールを追加」の
導線を出す。カレンダーだけでは何も始められないため。

### 8.2 月カレンダーのセル

| 要素 | 内容 |
|---|---|
| 日付 | 平日=標準色 / 土=青 / 日・祝=赤 / 休業日=グレー背景 |
| 祝日名 | 祝日の場合に小さく表示（例「敬老の日」） |
| 休業ラベル | `closedRanges` に該当する場合その label（例「年末年始休業」） |
| 予定チップ | ルールの色＋タイトル（省略しない）。補正済みなら向きと元の日を示す記号を付す |
| 事前通知チップ | 破線枠でルール色を継承 |
| 今日 | 枠を強調 |
| 選択中の日 | 枠と淡い背景で強調 |
| ホバー | セル全体がクリック可能であることを背景色で示す |

補正済みチップの記号は `←10` `→10` の形にする。`←` は前倒し、`→` は後ろ倒し、
数字は補正前の日。向きと由来の両方を2〜3文字で示せるため、`⟳` だけを出すより情報量が多く、
`both` で前後に分かれた2件を並べたときにどちらがどちらか一目で分かる。

祝日名と休業ラベルが両方該当する日（元日と年末年始休業が重なる 1/1 など）は、
**祝日名を優先して表示する**。休業していること自体は背景色が示しており、
そこに「年末年始休業」とだけ出すと「元日」という情報が失われるため。

予定チップにホバーすると、補正前の日付・補正方向・備考をツールチップ表示する。

**チップは件数でも文字数でも省略しない。** 予定名は全文を折り返し、セルは中身に
合わせて縦に伸ばす。件数の上限も設けない。反復ルールから導く性質上、1日に極端な
件数が並ぶことは考えにくく、省略するよりページをスクロールさせるほうが実務では読みやすい。

> **実装上の注意**: 以前は `-webkit-line-clamp` で2行に制限していたが、標準プロパティ
> `line-clamp` を部分実装したブラウザ（Android Chrome で確認）では
> **省略記号は出るのに溢れた行が切り取られず、セルの外へはみ出した**。
> clamp に頼らず、折り返しとセルの伸長で対処する。

**セルのどこをクリックしても**その日の詳細をモーダルで開く。日付の数字だけを
当たり判定にすると、特にスマートフォンでは狙いにくいため。

- 日付の数字は `<button>` のままにしておき、キーボードとスクリーンリーダーからの
  入口として残す。button の click はセルへ伝播するので、ハンドラはセル側に1つだけ
  置いて二重発火を避ける
- 予定名をドラッグで選択しただけのときは開かない（選択範囲があれば無視する）

**予定の出し方は「内容」と「点」から選べる（既定は内容）。**

7列の月表示ではセル幅がおよそ50pxしかなく、狭い画面で日本語の予定名を入れると
1〜2文字ずつ縦に割れ、1か月が画面3枚分（3,600px）に伸びる。かといって、
いつも点だけでは「何があるか」が読めない。どちらが良いかは、画面の幅だけでなく
予定の数や、そのとき何を知りたいかで変わる。

そこで**画面幅では決めず、利用者が選んだものを覚える**。

| 出し方 | 中身 | 向いている場面 |
|---|---|---|
| 内容（既定） | 予定名まで出す | 何があるかをその場で読みたい |
| 点 | 色の点だけ。件数は点の数で分かる | 1か月を見渡したい・幅が足りない |

点のときは凡例も点向けの説明に差し替える。中身は日付を押して詳細で読むか、
一覧表示へ切り替えて読む。

### 8.3 一覧表示

今日から N 日分（30 / 90 / 180 / 365 から選択、既定 90）の発生日を時系列で列挙する。
カレンダーが「今月の形」を見るためのものなのに対し、こちらは「これから何が来るか」を
追うためのもの。印刷して配る用途も想定する。

列は `日付 / 曜日 / 予定 / 補正 / 内容`。

- 日付と曜日は、その日の**最初の行にだけ**出す。同じ日の予定がひとかたまりに見え、
  日付が変わる位置が目で追える
- 曜日は日・祝を赤、土を青にし、祝日名を添える
- 補正列には `←25` `→25`。事前通知の行には「2026-09-25 の準備」と由来を出す
- 今日の行は背景で強調する
- 日付をクリックすると日付の詳細、予定名をクリックするとそのルールの編集を開く

表示（カレンダー／一覧）と先読み日数は設定として保存する。

**カレンダーと期間を引き継ぐ。** 「いま見ている予定を一覧にする」と考えるのが
自然なので、別の月を見てから切り替えたらその月から並べる。今月を見ているときは
「今日から」のまま（過去の予定まで遡らせない）。逆向き（一覧→カレンダー）も同じ。

起点は日付で選べる。今日から見たい場面も残したいので、〈今日から〉で戻せる。
入力は**実在する日付だけ**を受け付ける（`isValidDateStr`）。`<input type="date">`
でも `20260-09-01` のような5桁の年がそのまま届くことがあり、そのまま渡すと
日付の解釈で例外になって画面が描けなくなる。弾いたら元の値に戻し、理由を出す。

同じ表示をもう一度押しただけでは起点を動かさない。押すたびに戻ると、選び直した
起点が黙って消える。

収録範囲の警告も、書き出しと同じ「いま見えている期間」（`visibleRange`）に対して
出す。起点を動かしても追従させるため。

### 8.4 ルール編集フォーム

- 反復条件は「毎月N日 / 第N営業日 / 第N曜日 / 毎週」のタブで切替。
  種類を切り替えても、それぞれの入力内容は下書きとして保持する
- 日と対象月は 1〜31／1〜12 のトグルボタン群で選ぶ。複数選択がそのまま
  「毎月10日と25日」「3・6・9・12月」になり、入力と結果の対応が明快になる
- 「四半期」「半期」「毎月」はプリセットボタンとして提示し、内部的に `months` へ変換。
  対象月を1つだけ選べば年次になる
- 条件付きの入力欄（隔週の基準日、2月に無い日の扱い、当月内補正）は、
  関係するときだけ出す。設問が減るほど迷いが減る
- **フォーム下部に「次の10回」プレビューを常時表示**
  → 補正の効き方をその場で確認できるようにする。誤設定を最も効果的に防ぐ。
  補正された回は元の日付と方向（⟳ 2026-12-31 から前倒し）も併記する
- 保存前にバリデーション（§10.2）。エラーがある間はプレビューを出さず、
  何を直せばよいかだけを示す

**似たルールは複製から作る。** 「25日締め」と「末日締め」のように、1か所だけ
違うルールを何本も作ることが多い。一から組み直させると、営業日カレンダーや
グループの指定を写し忘れる。一覧の〈複製〉で設定を写した編集画面を開く。

作り直すのは `id` と日時、そして前後の予定の `id` だけ。既定値ごと被せると、
写したはずの営業日カレンダーや繰り返しまで初期状態へ戻る（実際に一度そうなった）。
前後の予定の `id` を残すと、書き出したときに元の予定を上書きしてしまう。

押した時点では保存しない。断りなく増やすと、一覧に似た名前が並んで
見分けがつかなくなる。名前を直してから保存してもらう。

**画面に出しっぱなしにする文章は削る。** 見出し・説明文・補足・言い換えが
積み重なると、設定そのものが遠くなる。常時出すのは短い1文にとどめ、
詳しい例は「設定例を見る」へ畳む。エラーも同じで、詳しい文言は該当欄の直下に
置き、保存欄には「修正が必要な項目が 2 件あります（前後の予定 1 件目）」と
件数と場所だけを出す（同じ文を二度読ませない）。

直近1組の日付は年を先に1度だけ出し、各予定は `9/25（金）` と短く書く。
`2026-09-25（金）` を4つ並べると、年が繰り返されるだけで肝心の日が読み取りにくい。
ただし**本体と違う年のものには年を付ける**（`2027/1/8（金）`）。年末年始の
準備・フォローは年をまたぐので、`12/31 → 1/8` だと翌年の1月8日が同じ年に見える。

**入力途中で閉じるときは確認する。** Esc・×・背景クリックはどれも起こりやすく、
確認なしに閉じると前後の予定まで組んだ内容が消える。開いた直後の姿を覚えておき
（`RuleEditor.isDirty`）、変わっているときだけ尋ねる。読み込みの整え（前後予定の
id 付けなど）が済んだあとを基準にする。そこより前に取ると、開いただけで
「変更あり」になってしまう。

**保存前の値になっていない入力も「変更あり」として数える。** 前後予定は
「大きさ」と「向き」を別に持ち（`TimingState`）、片方が空や 0 のあいだは
モデルへ書き戻さない。モデルだけを比べると、数字を消しただけ・`0` を打ち込んだ
だけの状態が「変更なし」になり、確認なしで閉じて入力が消えていた。比較には
`TimingState` も含める。

尋ねる場所は閉じる経路すべて。`createDialog` に `canClose` を渡し、Esc は
`cancel` イベントを打ち消して止める。別の画面へ移る（ヘッダーのボタン）ときも
同じ確認を通す。保存後など、こちらから閉じるときは `close(true)` で確認を飛ばす。

### 8.5 日付の詳細

日付をクリックするとモーダルで開く。

- 日付・曜日・その日が営業日か休業日か（休業なら理由）
- その日の予定を全件（チップの上限に関係なく）。補正されたものは
  「本来は 2026-10-10（休業日）。前営業日へ前倒し。」のように由来を文章で示す
- 各項目から該当ルールの編集へ移動できる
- 前日／翌日ボタンで日を送る。月をまたぐ場合は表示月も追従する

**その日を対象に計算する。** カレンダーが描いている月ぶんの結果から拾っていたため、
一覧の起点を先の月にしてその日を開くと「予定はありません」と出ていた。一覧は
月をまたいで並ぶので、カレンダーの月と開いた日は一致しない。

### 8.6 ヘルプ

**画面だけでは伝わらないものを、読めば一通り使えるところまで書く。**
営業日補正・決算月基準・グループ・前後の予定は、いずれも一般的なカレンダーに
無い概念で、UI をいくら整えても「そもそも何ができるのか」は伝わらない。

節は次のとおり。長くなるので先頭に目次を置き、困っている所へ直接飛べるようにする。
頭から順に読ませるものではない。

| 節 | 中身 |
|---|---|
| このアプリは何をするもの？ | ほかのカレンダーとの違い、単発の予定を扱わない理由 |
| はじめの3ステップ | サンプル追加 → 営業日カレンダー設定 → 書き出し |
| 繰り返しの種類 | 5種類それぞれの向き不向き |
| 休業日にあたったとき | 補正5種と「同じ月に収める」 |
| 決算月から逆算する | 設定の場所、よく使う形、追従の範囲 |
| 前後の予定 | 準備日とフォローの例、営業日／暦日の違い |
| グループで束ねる | 付け方、絞り込み、書き出しへの引き継ぎ |
| カレンダーの見かた | 記号、内容／点の切り替え、一覧 |
| 営業日カレンダー | 自社／銀行、決算月、休業日の指定 |
| 外部カレンダーへ書き出す | 取り込み手順、形式の選び方、二重取り込み |
| サンプル | 束の種類、既存ルールへの影響 |
| データの保存 | 保存先、バックアップ、オフライン |
| 思ったとおりに出ないとき | 予定が見えない／日付がずれる／決算月が効かない など |

最後の「思ったとおりに出ないとき」は、実際に問い合わせを受けた内容と、
仕様上そう見えるだけのもの（第N営業日で補正が選べない等）を並べる。

「反復ルール」と「営業日補正」はこのアプリ固有の概念のため、画面内に説明を置く。
繰り返しの種類、補正の種類（`both` を含む）、カレンダーの記号、営業日カレンダー、
データの保存先とバックアップ方法を扱う。

**引き方は2通り。タブで面を分ける。** 索引と解説を1枚に積むと、上から順に
読むしかない長さになる。目当ての引き方を選んでから読めるようにする。
既定は「やりたいことから探す」（初めての人が最初に目にするのはこちらであってほしい）。

タブは左右の矢印（と Home / End）でも移れる。選ばれていないタブは
`tabindex="-1"` なので、矢印を受けないとキーボードだけでは切り替えられない。
選択と同時に焦点も動かす（押した先が見えていないと迷う）。

**「やりたいことから探す」。** 節見出しは覚えたあとなら探せるが、
初めての人は自分の業務をどの項目に置き換えればよいかから悩む。
「毎月25日の給与振込を作りたい。25日が休みなら前営業日にしたい」のように
実務の言葉のまま並べ、開くと手順が出る。

**種類でまとめる**（予定を作る / 営業日と決算月を設定する / 書き出す・見やすくする /
困ったとき）。平らに並べると、目で追うだけで疲れる。
一覧はすべて畳んでおく。開いた状態で並べると縦に長くなりすぎて、目当ての
ものを探すのがかえって大変になる。

**読むだけで終わらせない。** 各項目に「ルールを作る」「書き出しを開く」
「営業日・決算月の設定を開く」など、その場から始める入口を1つ添える
（`HelpAction`）。読んで閉じたあとに操作を探し直させると、そこでまた迷う。
操作を受け取れないときは、その入口を出さない（押しても何も起きないボタンを
置かないため）。

### 8.7 月の移動

年月をクリックすると開く。年を ‹ › で送り、12か月のボタンから選ぶ。
今日が属する月には印を付け、いま何月から離れているかの手がかりにする。
「今日の月へ」で一度に戻れる。

### 8.8 配色モード

`auto`（OS の設定に従う）/ `light` / `dark` の3状態を巡回で切り替える。
選択は設定として保存し、次回起動時にも適用する。

CSS では light のトークンを `:root` に置き、dark を
`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` と
`:root[data-theme="dark"]` の両方に定義する。これにより、OS がダークでも
明示的に light を選べば上書きできる。

### 8.9 印刷

カレンダー・一覧のどちらも、そのまま印刷して配れる状態にする。

- 用紙では**常に白地・黒文字**にする。配色トークンのダーク定義は `:root` より
  詳細度が高いセレクタに置いてあるため、印刷時の上書きも**同じセレクタを並べて**
  行う。素の `:root` だけに書くと詳細度で負け、ダークモードのまま印刷したときに
  文字が薄いまま残る（実際に一度その状態になった。`tests/printCss.test.ts` が
  構造を検査する）
- 操作用の要素（ヘッダー・モーダル・バナー・凡例・リンク）は印刷しない
- 画面ではヘッダーが月やレンジを示しているが紙には残らないため、
  印刷時だけ見出し（`2026年9月` / `2026-09-05 〜 2026-12-03 の予定`）を出す
- 営業日数と祝日データの出典は、紙に残る情報として意味があるので印刷する
- 今日の枠は色ではなく太線で示す。単色印刷でも分かるようにするため
- 予定チップは塗りではなく枠線にする（インク節約と可読性）
- 週の行・一覧の行が用紙をまたいで割れないようにする（`break-inside: avoid`）

### 8.10 アプリ名と版

画面上部にアプリ名（**Business Days Schedule**）、何をするものかの一言
（**反復ルールを組んで、Outlook / Google カレンダーへ**）、版（`v1.4.0`）を常に出す。

名前と一言は `src/core/buildInfo.ts` の `APP_NAME` / `APP_TAGLINE` に一本化し、
画面・書き出しのカレンダー名・文書で同じ言葉を使う。ばらけると同じものに見えなくなる。

一言を添えるのは、「営業日カレンダー」だけでは*作ったものを会社の予定表へ持ち込める*
という肝心の部分が伝わらないため。

版を出すのは、静的サイトは「いま見ているものがいつのものか」が分かりにくく、
不具合の報告を受けたときに版を突き合わせられないと原因を追えないため。

版・ビルド日時・コミットはビルド時に埋め込む（`vite.config.ts` の `define`）。
設定の「このアプリについて」に詳細を、フッターにも版を出す。印刷時はアプリ名と版を非表示にする。

### 8.11 アクセシビリティ

- **ランドマーク**: `header` / `main` / `footer` を分ける。冒頭に「本文へ移動」の
  スキップリンクを置く
- **フォーム**: 入力欄が1つに定まる `field` は `label`/`for` で結ぶ。トグル群は
  `role="group"` と `aria-labelledby`。説明は `aria-describedby`。
  1つの枠に複数の入力欄が並ぶ場合（期間の開始・終了など）は欄ごとに `aria-label` を付ける
  - ただし**ボタンにロールをかぶせない**。`role="group"` を付けるとボタンでなくなる
    （実際にこれで書き出しボタンが押せなくなった）
- **カレンダーのキーボード操作**: 42個のボタンを全部タブ順に入れると通り抜けるだけで
  大変になるため、代表の1つだけを `tabindex="0"` にし（roving tabindex）、
  矢印キー・Home/End・Page Up/Down で移動する。月をまたぐ移動では、描き直したあとに
  同じ日へフォーカスを戻す
- **通知**: バナーと検証結果は `role="status"` の live region に置く
- **コントラスト**: 淡色は AA を満たす値にする。
  前後の月のセルを**透明度で薄くしない**。文字のコントラストが落ちて読めなくなるため、
  背景と日付の色で区別する（実際に AA を満たしていなかった）

`axe-core` を E2E に組み込み、主要画面（カレンダー・一覧・ルール編集・設定・ヘルプ）で
違反ゼロを保つ。

### 8.12 設定画面

- 営業日カレンダーの編集（週末曜日、祝日を使うか、**決算月**、休業期間、臨時休業日、臨時営業日）
  - 変更するとその場で「今月の営業日は N 日です」を更新し、左のカレンダーも描き直す。
    設定の影響を数字と実物の双方で確かめられるようにするため
- 祝日データの出典・取得日時・収録範囲・二次検証の結果を表示
- JSON エクスポート／インポート（置き換え／マージ）
- 全データ削除

## 9. 永続化とデータ入出力

### 9.1 保存先

`localStorage` を正とする。サーバー・認証なし。

| キー | 内容 |
|---|---|
| `bds.v1.rules` | `Rule[]` |
| `bds.v1.calendars` | `BusinessCalendar[]` |
| `bds.v1.prefs` | 表示設定（既定ビュー、一覧の日数、配色モード） |
| `bds.v1.schemaVersion` | スキーマ版数。マイグレーションの起点 |

`localStorage` が使えない環境（プライベートモード等）では、メモリ上で動作しつつ
「この端末には保存されません」と警告バナーを出す。

**書き戻すのは触ったキーだけ**（`saveRules` / `saveCalendars` / `savePreferences`）。
まとめて書く `saveState` は、取り込み・全消去のように全体を置き換えるときだけ使う。
配色や一覧の日数を変えただけで全部を書き戻すと、そのタブが起動時に読んだ古い
ルール一覧で上書きしてしまい、別のタブで作ったルールが消える。

あわせて `storage` イベントを購読し、別のタブの保存を取り込む（`watchOtherTabs`）。
編集中の画面は開いたままにする（書きかけを消さないため）。

### 9.2 エクスポート／インポート

単一 JSON ファイル `business-days-schedule-YYYYMMDD.json`:

```jsonc
{
  "schemaVersion": 1,
  "exportedAt": "2026-09-04T10:00:00+09:00",
  "calendars": [ /* BusinessCalendar[] */ ],
  "rules": [ /* Rule[] */ ],
  "prefs": { }
}
```

- インポート時は「置換」「マージ（ID 重複は取り込み側を採用）」を選択
- スキーマ検証に失敗したファイルは取り込まず、エラー箇所を明示
- 端末間の移行・バックアップ・バージョン管理（このファイル自体を Git 管理する）に使う

### 9.3 サンプル定義の同梱

`public/data/samples/` に、種類ごとに分けたサンプルの束を置く。
`index.json` が束の一覧（id・名前・説明・ファイル・件数）を持ち、UI はこれを読んで並べる。

| 束 | 内容 |
|---|---|
| `business-basics` | 給与振込・月次締め・請求書発行・支払処理・定例会議 |
| `tax` | 源泉所得税、住民税、社会保険、年度更新、算定基礎届、法定調書、償却資産申告。申告期限・期首・中間申告・四半期は `fiscalRelative` で決算月に追従する |
| `receivables` | 締め日、請求書発行、入金予定（`both`）、入金消込、督促 |
| `payables` | 仕入請求書の受領、支払データ作成、買掛金振込、給与、賞与、経費精算 |
| `meetings` | 週次報告、月次定例、経営会議、四半期報告、隔週1on1 |

- **使い始めたあとでも追加できる。** ルール一覧に「サンプル」ボタンを常設する。
  新規ルールの追加とはボタンを分ける（目的が違うため）。
  空のときにしか導線を出していなかったころは、使い始めると到達できなくなっていた
- 追加は**マージ**なので既存のルールは消えない。同じ束を再度追加すると、
  その束のルールだけが元の内容へ戻る（ID が束ごとに固定されているため）
- **束は `calendars` を持たない。** 追加のたびに利用者の営業日設定を上書きしてしまうため、
  空配列にしてある（マージ時に現在の設定がそのまま残る）
- 日付や名称は目安であり、正確性より「型として使えること」を優先する。
  その旨を画面に明記する

### 9.4 外部カレンダーへの書き出し

Google カレンダーや Outlook など、会社指定のカレンダーへ取り込むための書き出し。

**反復ルールそのものは渡さない。** 営業日補正は相手のカレンダーでは再現できないため、
指定期間の発生日へ展開し、確定済みの日付を持つ単発の予定として渡す。
期間の指定が必須なのはこのため。期間が過ぎたら書き出し直す。

| 形式 | 用途 |
|---|---|
| **iCalendar (.ics)** | 既定。Google・Outlook・Apple のいずれでも読める |
| **CSV** | Google カレンダーの取り込みと、表計算で中身を確かめたいとき |

CSV を既定にしないのは、Outlook.com がカレンダーの CSV 取り込みに対応していないため。

**グループ単位でも書き出せる。** 取り込み先でも束ごとに別のカレンダーへ入れておくと、
あとで丸ごと消せる。画面で絞り込んでいるときはその束を初期値にする。
見ているものと渡すものが食い違うと、画面に無い予定が取り込み先へ紛れ込むためである。
カレンダー名（`X-WR-CALNAME`）とファイル名にも束の名前を混ぜ、取り込み先と手元の
両方で見分けられるようにする。グループ名は自由入力なので、ファイル名に使えない
文字は落とし、残らなければ足さない。

**期間の初期値は「今月1日〜末日」。** 試しに1回押しただけで1年分がメインの予定表へ
流れ込むと、消して回るのが大変で取り返しもつきにくい。プリセットも月の区切り
（今月／来月／3か月／6か月／1年）にそろえ、いま選ばれているものを押された状態で示す。
件数が60件を超えるときは、短い期間から試すよう画面上で促す。

**取り込み先は専用のカレンダーを作るよう、書き出す前に必ず目に入る位置で勧める。**
取り込みは「元に戻す」が効かない操作であり、いつもの予定表へ直接入れると
一件ずつ消すことになる。Outlook・Google それぞれの入れ物の作り方まで書く。

**取り込んだ先での読みやすさを重視する**（このアプリはルール作りに徹し、
日々見るのは相手のカレンダーであるため）。

| 出しかた | 例 |
|---|---|
| そのままの日 | `給与振込` |
| 休業日で前へ動いた | `給与振込（繰上）` |
| 休業日で後ろへ動いた | `給与振込（繰下）` |
| 事前通知（準備日） | `【振込データ作成】給与振込` |

件名は予定の名前を頭に置く。取り込み先の月表示では先頭の数文字しか見えないため。
説明は「見出し: 中身」の形にし（`補正:` / `対象:` / `ルール:` / `メモ:`）、
1行に潰れて表示されても頭から読めるようにする。日付には曜日を添える。

実装上の要点:

- 終日予定として出す。iCalendar の `DTEND` は排他的なので**翌日**を指定する
- `UID` は `ルールID-種別-基準日-系列-通知番号@business-days-schedule` の形にする。
  内容だけから決まるので、書き出す期間や出力順を変えても同じ予定には同じ値が付く。

  **両側補正（`both`）では、子（準備日・フォロー）も親の向きを引き継ぐ**
  （`Occurrence.seriesDirection`）。子は自身が動いていないので `shiftDirection` は
  `null` になり、それだけでは前倒し側と後ろ倒し側の2系列を見分けられない。
  見分けられないまま重複回避の連番に頼ると、書き出す期間によって連番の割り当てが
  変わり、**狭い期間で書き出したときに別の日の予定を上書きする**。実際に再現した。

- **ただし「重複しない」と約束はできない。** UID を見て同じ予定と判断するかどうかは
  取り込み先の実装しだいで、こちらからは保証できない。CSV には識別子そのものが無い。
  画面・ヘルプ・README では「取り込み先しだい」と書き、短い期間で試すよう促す。
- **削除は伝わらない。** 書き出しはその時点の予定の写しで、取り消し
  （`METHOD:CANCEL` / `STATUS:CANCELLED`）を出していない。アプリ側でルールを消しても、
  既に取り込まれた予定は残る。専用カレンダーごと入れ替える運用を案内する
- iCalendar は1行75**オクテット**で折り返す（RFC 5545 §3.1）。日本語は1文字3オクテットに
  なるため、文字数で数えると規格違反になる。マルチバイト文字の途中では折らない
- 改行は CRLF。`,` `;` `\` と改行はエスケープする
- **補正の由来を `DESCRIPTION` に残す**（「補正: 本来は 2026-10-25（日）（休業日）。前営業日へ繰り上げ」）。
  取り込んだ先で日付だけ見ても理由が分からなくなるのを防ぐ
- `CATEGORIES:Business Days Schedule` を付ける。Outlook では色分けと絞り込みに使え、
  試しに入れた予定をまとめて消すときの手掛かりにもなる
- 予定は時間を埋めるものではなく目印なので `TRANSP:TRANSPARENT` を付ける。
  Outlook は `TRANSP` を見ないため、`X-MICROSOFT-CDO-BUSYSTATUS:FREE` と
  `X-MICROSOFT-CDO-ALLDAYEVENT:TRUE` でも同じことを伝える
- CSV には BOM を付ける。表計算ソフトで開いたときの文字化けを防ぐためで、
  Google カレンダーの取り込みは BOM 付きでも読める

## 10. 品質・エッジケース

### 10.1 テスト観点（Vitest / Playwright）

単体テスト（Vitest）に加えて、**保存と画面をまたぐ流れは E2E（Playwright）**で確かめる。
「編集 → 再読込 → 再追加」のような順序依存の不具合は単体テストの構造では拾えず、
実際にサンプル再追加で編集内容が失われる不具合を取り逃がしていた。

E2E は本番ビルド（`dist/`）を素の静的配信で動かす（`scripts/serve-dist.ts`）。
GitHub Pages と同じ条件に近づけ、公開後にだけ壊れる不具合を拾うため。
デスクトップ幅とスマートフォン幅の2構成で実行する。


| 領域 | ケース |
|---|---|
| 営業日判定 | `openDates` が祝日・週末より優先されること／`closedRanges` の年跨ぎ（12-29〜01-03） |
| monthlyByDay | 31日指定 × 2月（clamp / skip）／うるう年 2/29／`"last"` の各月 |
| monthlyByWeekday | 第5週が無い月／`nth: -1` と `nth: 5` が一致する月・しない月 |
| monthlyByBusinessDay | 営業日数が不足する月／`-1` が月末営業日と一致すること |
| weekly | `interval: 2` の位相が `anchor` 起点で正しいこと／年跨ぎで位相がずれないこと |
| 補正 | `prev`/`next`/`nearest`（同距離は prev）／`both` が前後2件を返すこと／`keepInMonth` の反転と `both` での片側除外／連続休業（GW・年末年始）の跨ぎ |
| 通知 | `unit: "business"` が休業日をスキップすること |
| 境界 | 表示範囲の端で補正により入退場する発生日／`period` 境界 |
| 日付演算 | TZ を UTC / Asia/Tokyo / America/New_York に切り替えても結果が同一であること |
| I/O | 不正 JSON のインポートが拒否されること／エクスポート→インポートの往復同一性 |
| 同梱データ | `src/data/holidays.json` が実在日付・昇順・今年と来年をカバーし、出典の全期間を保っていること |
| サンプル | 全束がそのまま取り込め、警告なしで1年分展開できること／束が `calendars` を持たないこと／ID が束をまたいで衝突しないこと／一覧とファイルが一致すること |
| 書き出し | iCalendar の折り返しが75オクテットでマルチバイトを壊さないこと／`DTEND` が翌日であること／`UID` が安定していること／CSV の列がずれないこと／件名で補正と準備日が見分けられること／分類・終日・空き時間の指定が入ること／初期範囲が今月であること |
| 実務ユースケース | §6 の17件が各1ルールで意図どおりの日付になること |
| 決算月 | 決算月を変えると申告期限・期首・四半期がまとめて動くこと／年をまたぐずれ／うるう年／未設定時の既定（3月）／営業日補正との組み合わせ |
| 表示 | 休業日・祝日・補正マーク（`←10`/`→10`）がマークアップに現れること／広い画面では件数と文字数のどちらも省略しないこと／狭い画面では点で示し1か月が縦に伸びないこと／ルール名の HTML がエスケープされること |
| 一覧 | 日付昇順であること／同じ日の2件目以降が日付を繰り返さないこと／補正と事前通知の由来が出ること |
| 印刷 | 印刷ブロックがダークと同じセレクタをすべて上書きすること／操作用の要素を隠し、紙に残す情報を出すこと |
| 事前通知の範囲 | 60営業日前・60暦日前・年をまたぐ通知が、通知日を含む表示で出ること |
| 壊れた入力 | 任意の値で `validateRule` / `validateCalendar` が例外を投げないこと／壊れた localStorage でも起動できること／巨大な通知日数を弾くこと |
| サンプルの取り込み | `add` が既存 ID を触らないこと／`merge` が明示操作のときだけ上書きすること |
| グループ | 空白差を吸収すること／未分類を取り出せること／消えた束を選んでいたら「すべて」へ戻すこと／一覧が束ごとに分かれ未分類が最後に来ること |
| 予定の出し方 | 既定が「内容」であること／点にすると名前が隠れ縦に詰まること／選択が再読込後も残ること／凡例が入れ替わること |
| 前後の予定 | 正負どちらの offset も受け付け 0 を弾くこと／向きどおりに日付が出ること／本体が範囲外の長いフォローを取りこぼさないこと／本体が補正で動けば一緒に動くこと／同じ日で本体→準備日→フォローの順に並ぶこと／日付を決められないものを警告に出すこと |
| UID の安定性 | 狭い期間で書き出しても広い期間と同じ日付に同じ UID が付くこと／両側補正の子予定に別々の UID が付くこと／重複回避の連番に頼っていないこと／両側補正でなければ向きが UID に入らないこと／前後の予定を1件消しても残りの UID が変わらないこと／並べ替えても入れ替わらないこと／id を持たない古いデータの UID が変わらないこと |
| 書き出し画面 | 日付欄を空にすると書き出せないこと／準備日とフォローを別々に外せること／開始日・終了日に名前が付いていること |
| 印刷 | 画面用の操作を出さないこと／点表示のままでも予定名が出ること／絞り込み中のグループを見出しとして残すこと |
| プレビュー | 本体に紐づく準備日・フォローを実際の日付で、前→本体→後の順に並べること／探索の区切りをまたぐものが欠けないこと／実際の展開と同じ日付になること／直近1組を詳細を開かずに見せること |
| 祝日データの代替 | 取得時刻の新しいほうを選ぶこと／公開中の版を確認できないときは止めること／未公開（404）なら代替してよいこと／どちらも読めなければ止めること |
| ヘルプ | 主要な概念の節が揃っていること／目次から各節へ飛べること／つまずきの答えが載っていること |
| サンプル画面 | 内容の一覧を開いたあと畳めること／畳んでも取得済みの中身を捨てないこと |
| 月の移動 | 年をまたいで選べること／表示中の月と今日の月に印が付くこと |
| スワイプ | 横が優勢なときだけ反応すること／縦スクロールと2本指を無視すること／直後の click を1回だけ止めること |
| スタイル | `[hidden]` が `!important` で効いていること（作者スタイルの display 指定に負けないため） |
| セルの操作 | 数字・余白・予定チップのいずれをクリックしても1回だけ詳細が開くこと／文字選択中は開かないこと |
| モーダル | 文書へ挿入してから開くこと（`showModal()` の制約）／背景クリックと閉じるボタンで閉じること／中身だけ差し替えられること |
| 日付詳細 | 営業日／休業理由の表示、補正の由来、上限を超える件数でも全件出ること |
| 配色 | `data-theme` の付け外しと巡回順 |
| 文言 | ルールの日本語要約（「毎月末から2営業日前」など）が崩れないこと |
| 編集 | 入力を変えるとプレビューが即座に追従すること／不正な設定では保存できないこと／編集中に元のルールを書き換えないこと |
| 設定 | 週末曜日・臨時営業日の変更が営業日数と表示に反映されること |
| 休業期間の月日 | `13-01` や `02-30` を確定させないこと／取り込み時に弾くこと／すでに保存されていても、その1件を無視して残りが動くこと |
| 保存の切り分け | 表示設定の保存が別のタブのルールを消さないこと／別のタブの保存を取り込むこと／編集中は画面を描き直さないこと |
| 探索範囲 | 同じ前後予定を何件付けても探索範囲が伸びないこと／そのルールのカレンダーで数えること／月単位の展開でも年単位と同じ前後予定が出ること |
| 警告の対象 | 表示範囲の外の月について警告を出さないこと／日付に紐づかない警告は残すこと |
| 警告の分類 | 「書き出されません」「別のカレンダーで計算」「前後が逆」を混ぜないこと |
| 一覧の起点 | 実在しない日付を弾いて元に戻すこと／同じ表示を押しても起点が戻らないこと／起点を先の月にしても日付詳細に予定が出ること |

祝日データはテスト用に固定スナップショットを使い、外部取得に依存させない。

### 10.2 バリデーション

`validateRule` / `validateCalendar` は**任意の値**を受け取りうる前提で書く（§13）。

- 型そのものを確かめる（文字列か、配列か、真偽値か）。欠けていれば issue にする
- `weekly` は `weekdays` が1つ以上
- `1 <= interval <= 120`
- `days` の要素は 1〜31 または `"last"`
- `period.start <= period.end`
- `notices[].offset` は `-1` 〜 `-365` の整数。
  **上限は必須**。営業日換算で巨大な値を渡されると、数えるだけで固まるため
- 件数・文字数の上限（タイトル200字、メモ2000字、通知20件、除外日1000件）
- 保存時にプレビューが0件になるルールは警告（保存自体は許可）

### 10.3 非機能

| 項目 | 目標 |
|---|---|
| 初期表示 | 3G 相当で 2 秒以内（バンドル < 150KB gzip、外部ランタイム依存なし） |
| オフライン | 祝日 JSON をキャッシュし、2回目以降はオフラインで動作（Service Worker は v2 で検討） |
| a11y | WCAG 2.1 AA（axe-core で自動検査）。キーボードだけで操作可能、コントラスト比 4.5:1 以上、色のみに依存しない情報伝達 |
| オフライン | 一度開いたあとは通信が無くても表示・操作できる |
| ブラウザ | 直近2バージョンの Chrome / Edge / Safari / Firefox |

## 13. オフライン対応

一度開いたあとは、通信が無くても表示・操作できるようにする。
外出先や電波の悪い場所で開けないと、日々の道具としては使えないため。

`scripts/build-sw.ts` がビルド後の `dist/` を走査し、事前キャッシュ一覧を埋め込んだ
`sw.js` を生成する。一覧を手で持つと、資産名のハッシュが変わるたびに更新漏れが起きる。
キャッシュ名は中身のハッシュから決めるので、内容が変われば必ず名前が変わり、
古いキャッシュが残り続けない。

| 対象 | 方針 |
|---|---|
| 画面遷移（navigate） | ネットワーク優先。オフラインのときだけキャッシュへ |
| ハッシュ付きの資産 | キャッシュ優先。URL が内容と対応しているため古いものを掴まない |
| 祝日データ・サンプル | ネットワーク優先（5秒で打切り）。通信・形式エラー時はキャッシュ。保存完了までwaitUntilで処理を維持 |

**更新は勝手に適用しない。** 新しい版を検知したら画面下に案内を出し、
利用者が「再読み込み」を選んだときだけ切り替える。編集途中のフォームを
黙って作り直さないため。

**ただし「新しい Service Worker が控えている」は「画面が古い」とは限らない。**
画面遷移はネットワーク優先で、資産名には内容のハッシュが入っている。だから
オンラインで開いた時点の画面は既に最新版になっており、そこで案内を出すと
「最新版を見ているのに更新を促され、押しても何も変わらない」ことになる。
実際にその状態になっていた。

案内を出す前に、控えている版へ資産一覧を尋ねる（`PRECACHE_MANIFEST` を
`MessageChannel` で問い合わせ、3秒で打切り）。いま画面が読み込んでいる
`script[src]` と `link[rel=stylesheet]` がすべてその一覧に入っていれば、画面は
既に最新なので**案内を出さずに黙って切り替える**（`skipWaiting` だけ送る。
`updateAccepted` を立てないので読み込み直しは起きず、オフライン用のキャッシュ
だけが新しくなる）。判断材料が無いとき（資産を1つも拾えない、答えが返らない）は
これまでどおり案内を出す。黙って切り替えるより害が小さい。

開いたままの画面が古くなった場合は、資産名が一覧と食い違うので案内が出る。
`e2e/updatePrompt.spec.ts` が両方向とも検出する（実際に作り直して確かめる）。

> **注意**: `clients.claim()` は**初回登録でも** `controllerchange` を起こす。
> これを更新と取り違えて読み込み直すと、初めて開いた人が必ず1回リロードされ、
> 入力途中のものも巻き込む。実際にその状態になったため、
> 「利用者が更新を選んだかどうか」を見てから読み込み直す。
> `e2e/serviceWorker.spec.ts` が回帰を検出する。

開発中は登録しない（`import.meta.env.PROD` のときだけ）。キャッシュが邪魔になるため。

キャッシュ削除はこのアプリの `bds-` 名前空間に限定し、同一ホストの別アプリには触れない。

## 14. 堅牢性の方針

外から来る値は、型が正しいと仮定しない。`localStorage` も取り込む JSON も
利用者が差し替えられるため、TypeScript の型は実行時には何も保証しない。

- `validateRule` / `validateCalendar` は**どんな値を渡されても例外を投げない**。
  問題は issue として返しきる。1件の破損で起動不能になってはいけない
- 読み込み時は健全なものだけを残し、捨てた件数を利用者へ知らせる
- 実務でありえない大きさには上限を置く（§10.2）。特に事前通知のさかのぼり日数は、
  営業日換算で巨大な値を渡されると数えるだけで固まるため、上限を必須とする
- **計算に使う直前でも取り除く。** 検証を通さずに入った値でも壊れないよう、
  `createBusinessDayCalendar` は実在しない月日の休業期間を落としてから使う。
  ここで落とさないと、保存済みの1件で毎回同じところが例外になり、再読み込みでも
  戻せない（利用者に復旧手段が無い状態になる）

## 16. 操作導線

- 給与・支払・締め日・会議・自由入力から新規予定を作る。
- 色・メモ、対象月、有効期間・除外日は折りたたむ。設定済みの詳細は編集時に確認できる。
- 保存操作と要約・直近3回の日付をフォーム下端に固定する。
- 「事前通知」の画面表記は「準備日」。メール・プッシュ通知ではないことを明示する。
- サンプルは束単位でも必要な1件だけでも追加できる。
- 設定は会社・銀行・バックアップ・アプリ情報を切り替える。
- ICSの単一予定は補正方向をUIDへ含めない。両方向の予定だけ枝を区別する。
- 通知の探索末尾は、対象カレンダーで実際に営業日を数えて決める。
- JSONの置換・マージ・追加とlocalStorage読込の全経路で表示設定を正規化する。
- 保存は触ったキーだけへ書き戻し、別のタブの保存は`storage`イベントで取り込む。
- 探索範囲は最も遠い前後予定に合わせ、件数では伸ばさない。
- 書き出し前の警告は、出ないもの・別カレンダーで出るもの・前後が逆のものを分ける。
