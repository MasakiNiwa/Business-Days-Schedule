# Business Days Schedule — 仕様書 v1.0 (draft)

営業日の概念を持ち、休祝日にかかった予定を自動で前営業日／翌営業日にずらして表示する、
**反復ルール駆動**のカレンダー。GitHub Pages で静的公開する。

---

## 1. 目的とスコープ

### 1.1 解きたい課題

実務のスケジュールは「日付」ではなく「**ルール**」で決まっている。

- 給与振込は「毎月25日。ただし土日祝なら**前**営業日」
- 社会保険料の納付は「毎月末日。ただし土日祝なら**翌**営業日」
- 請求書発行は「毎月**第5営業日**」
- 支払処理は「**月末2営業日前**」

一般的なカレンダーアプリはこの「営業日補正」を持たないため、毎月人間が手で日付をずらしている。
本アプリはその補正を自動化することだけに集中する。

### 1.2 スコープ内 (In Scope)

| # | 機能 |
|---|---|
| F-1 | 日本の祝日データを自動更新して取り込む |
| F-2 | 営業日カレンダー（土日・祝日・自社休業日・臨時営業日）の定義 |
| F-3 | 反復ルールの追加・編集・削除・有効／無効切替 |
| F-4 | 反復ルールの営業日補正（前倒し／後ろ倒し／補正なし／最近接） |
| F-5 | 月カレンダー表示・一覧表示 |
| F-6 | N営業日前の事前通知（準備日）表示 |
| F-7 | ルール定義の JSON エクスポート／インポート |

### 1.3 スコープ外 (Out of Scope) — 意図的に作らない

| # | 非目標 | 理由 |
|---|---|---|
| N-1 | **ルールを持たない単発予定の登録** | 汎用カレンダーの領域。既存アプリに任せる。本アプリの一貫性（＝すべての表示はルールから導出される）を守る |
| N-2 | サーバー・ログイン・複数ユーザー同期 | 静的ホスティングの範囲を出ない |
| N-3 | 通知メール・プッシュ通知 | 画面表示のみ |
| N-4 | 日本以外の祝日 | v1 では対象外（データ層は差し替え可能に設計する） |

> N-1 の例外として **「ルールの除外日」** は許可する（例: 毎月10日のルールだが 2026-08-10 だけ無し）。
> これは新しい単発予定の追加ではなく、既存ルールの例外指定であるため方針と矛盾しない。

### 1.4 想定利用者

個人（バックオフィス／経理／総務／個人事業主）。ブラウザ1台で完結する。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| **休業日** | 営業日カレンダー上、業務を行わない日。週末＋祝日＋自社休業日から臨時営業日を除いたもの |
| **営業日** | 休業日でない日 |
| **祝日** | 「国民の祝日に関する法律」に基づく祝日・振替休日・国民の休日 |
| **ルール (Rule)** | 反復条件・営業日補正・期間などをまとめた1件の定義 |
| **発生日 (Occurrence)** | ルールを展開して得られる1つの日付 |
| **基準日 (Raw Date)** | 営業日補正を適用する前の日付 |
| **確定日 (Effective Date)** | 営業日補正を適用した後の、実際に表示される日付 |

## 3. 祝日データ

### 3.1 データソースの決定

内閣府 CSV (`https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv`) は
Shift_JIS・行末 CRLF・掲載範囲が「1955年〜翌年」に限られるなど扱いが難しい。

**一次ソースとして [`holiday-jp/holiday_jp`](https://github.com/holiday-jp/holiday_jp) の `holidays.yml` を採用する。**

| 項目 | 内容 |
|---|---|
| 取得 URL | `https://raw.githubusercontent.com/holiday-jp/holiday_jp/master/holidays.yml` |
| 収録範囲 | 1970-01-01 〜 2050-12-31（約1,330件） |
| 文字コード | UTF-8 |
| 形式 | `2026-01-01: 元日` の1行1レコード（YAMLマップ） |
| 振替休日 | 収録済み（例: `2026-05-06: こどもの日 振替休日`） |
| 国民の休日 | 収録済み（例: `2026-09-22: 休日`） |
| 更新 | 内閣府の発表に追随してメンテナンスされている |

採用理由:
- UTF-8 の素直なテキストで、パースに外部ライブラリ・文字コード変換が不要
- 将来分（春分・秋分の計算値を含む）まで収録されており、来年以降のカレンダーが空にならない
- GitHub 上のファイルなので取得が安定し、コミット SHA で版を固定・追跡できる

> **注意（正確性の限界）**: 春分の日・秋分の日は前年2月の官報公示で正式確定する。
> それ以前の年の値、および将来の祝日法改正・臨時の祝日（改元・オリンピック等）は反映されていない可能性がある。
> UI 上に「◯年◯月◯日時点のデータ」と出典を明示する（§8.5）。

### 3.2 二次ソースによる検証

一次ソースを盲信しないため、CI 上で内閣府 CSV との突合を行う。

**「実データが食い違う」と「内閣府サイトへ届かない」を区別する。** 取るべき行動が
正反対であり、まとめて失敗として扱うと誤った祝日データを公開しかねないため、
`scripts/verify-cao.ts` は終了コードで結果を分ける。

| 終了コード | 意味 | CI の動き |
|---|---|---|
| 0 | 一致 | 差分があればコミットし公開する。`verifiedAgainstCao: true` |
| 1 | **不一致** | **公開しない。** Issue を起票。`verifiedAgainstCao: false` |
| 2 | 確認できず（取得・解釈に失敗） | 既存データを維持したまま公開。Issue を起票。`verifiedAgainstCao: null` |

`verifiedAgainstCao` が `false` のときは、設定画面だけでなく**画面上部に常時バナー**を出す。
休業日の判定が誤っている可能性を、使う前に知らせる必要があるため。

### 3.3 生成物: `public/data/holidays.json`

```jsonc
{
  "meta": {
    "source": "holiday-jp/holiday_jp",
    "sourceUrl": "https://raw.githubusercontent.com/holiday-jp/holiday_jp/master/holidays.yml",
    "sourceSha": "a1b2c3d...",          // 取得時のコミット SHA
    "fetchedAt": "2026-09-04T18:00:00Z",
    "range": { "from": "1970-01-01", "to": "2050-12-31" },
    "count": 1329,
    "verifiedAgainstCao": true           // 二次検証の結果
  },
  "holidays": {
    "2026-01-01": "元日",
    "2026-01-12": "成人の日",
    "2026-05-06": "こどもの日 振替休日",
    "2026-09-22": "休日"
  }
}
```

- 全期間を単一ファイルで持つ（約48KB、gzip で数KB。分割の必要なし）
- 日付キーは `YYYY-MM-DD` 昇順で安定ソートし、差分を読みやすく保つ
- `meta.range` は暦年の境界へ丸める。収録最終日（2050-11-23 など）をそのまま範囲末尾にすると、
  その後の平日が「データ範囲外」と誤判定されてしまうため

### 3.4 更新ワークフロー `.github/workflows/update-holidays.yml`

| 項目 | 内容 |
|---|---|
| トリガー | `schedule`（毎週月曜 03:00 JST ＝ 日曜 18:00 UTC）＋ `workflow_dispatch` |
| 手順 | ① 一次ソース取得 → ② `holidays.json` 生成 → ③ 二次検証 → ④ 差分があればコミット |
| 差分なし | コミットせず正常終了（`git diff --quiet` で判定） |
| 取得失敗 | ワークフローを **失敗** させ、既存の `holidays.json` は保持する（空ファイルで上書きしない） |
| 権限 | `contents: write`, `issues: write` |

コミット後は Pages のデプロイワークフローが走り、公開サイトに反映される。

## 4. 営業日カレンダー

### 4.1 定義

```ts
type BusinessCalendar = {
  id: string;                 // "company" | "bank" | 任意
  name: string;               // 表示名
  fiscalYearEndMonth?: Month; // 決算月（事業年度の終わる月）。未設定なら3月
  weekendDays: Weekday[];     // 既定 [0, 6]（日・土）。土曜出勤なら [0]
  useNationalHolidays: boolean; // 既定 true
  closedRanges: AnnualRange[];  // 毎年繰り返す休業期間（年末年始・夏季休業など）
  closedDates: DateStr[];       // 臨時休業日（単発）
  openDates: DateStr[];         // 休業日だが営業する日（祝日出勤など）
};

type AnnualRange = {
  from: "MM-DD";   // 例 "12-29"
  to:   "MM-DD";   // 例 "01-03"（年をまたぐ指定を許可）
  label: string;   // "年末年始休業"
};
```

### 4.2 判定ロジック（優先順位）

```
isBusinessDay(date):
  1. openDates に含まれる            → 営業日   (最優先)
  2. closedDates に含まれる          → 休業日
  3. closedRanges のいずれかに該当   → 休業日
  4. useNationalHolidays かつ祝日     → 休業日
  5. weekendDays に曜日が含まれる     → 休業日
  6. それ以外                        → 営業日
```

`openDates` を最優先にすることで「祝日だが出社」を無条件に表現できる。

### 4.3 プリセット

| ID | 名称 | 定義 |
|---|---|---|
| `company` | 自社カレンダー（既定） | 土日＋祝日。年末年始 12/29〜1/3 を既定で休業に設定 |
| `bank` | 銀行休業日 | 土日＋祝日＋12/31〜1/3 |

年末年始の休業日数は会社ごとに異なるため、`company` の 12/29〜1/3 はあくまで初期値であり、
設定画面から変更できる。

ルールごとに `calendarId` を指定できる。
「社内締めは自社カレンダー、振込は銀行カレンダー」といった使い分けが1画面で成立する。

## 5. スケジュールルールのデータモデル

### 5.1 Rule

```ts
type Rule = {
  id: string;                 // UUID v4
  title: string;              // 例 "給与振込"
  color: ColorToken;          // プリセット8色から選択
  note?: string;              // 備考（ツールチップに表示）
  enabled: boolean;           // 一時的に無効化できる
  calendarId: string;         // 参照する営業日カレンダー（既定 "company"）

  recurrence: Recurrence;     // §5.2
  adjust: Adjustment;         // §5.3
  notices: Notice[];          // §5.4（事前通知）

  period: { start: DateStr | null; end: DateStr | null };  // 有効期間（null は無期限）
  skipDates: DateStr[];       // 除外する【基準日】のリスト

  createdAt: string;
  updatedAt: string;
};

type Weekday = 0 | 1 | 2 | 3 | 4 | 5 | 6;   // 0=日曜
type Month   = 1 | 2 | ... | 12;
type DateStr = `${number}-${number}-${number}`;  // "YYYY-MM-DD"
```

### 5.2 Recurrence（反復条件）— 4種類

種類を絞りつつ、`months` フィルタと配列指定の組み合わせで実務パターンを網羅する。

#### (a) `weekly` — 毎週 / 隔週

```ts
{
  type: "weekly",
  interval: number,      // 1=毎週, 2=隔週, 4=4週ごと
  weekdays: Weekday[],   // 例 [1, 5] = 月曜と金曜
  anchor?: DateStr       // interval >= 2 のときの位相基準（省略時は period.start、それも無ければ 1970-01-05(月)）
}
```

#### (b) `monthlyByDay` — 毎月N日 / 月末

```ts
{
  type: "monthlyByDay",
  interval: number,              // 1=毎月, 3=3か月ごと
  months?: Month[],              // 対象月フィルタ。省略＝全月。例 [3,6,9,12] で四半期
  days: (number | "last")[],     // 例 [25] / [10, 25] / ["last"]
  overflow: "clamp" | "skip"     // 31日指定で2月など、存在しない日の扱い。既定 "clamp"
}
```

- `"last"` は月の暦上の末日（2月なら28/29日）
- `overflow: "clamp"` … 30日指定 → 2月は28/29日に丸める
- `overflow: "skip"` … その月は発生させない

> **編集画面では 31 と `"last"` を分けない。** 31日を指定した月はすべて末日であり、
> 2つ並べても選ぶ側が迷うだけになる。トグルは `31 / 末日` の1つにまとめ、内部表現は
> `"last"` に寄せる。以前の版が保存した `31` も同じトグルとして扱う。
> これにより `days` に 29・30 以外の「存在しない日」は入らなくなるため、
> `overflow` の設問は29日・30日を選んだときだけ出す（§8.4）。
- `months` を1つだけ指定すれば年次ルールになる（例: `months:[4], days:[1]` = 毎年4月1日）

#### (c) `monthlyByWeekday` — 毎月第N曜日

```ts
{
  type: "monthlyByWeekday",
  interval: number,
  months?: Month[],
  nth: (1 | 2 | 3 | 4 | 5 | -1)[],   // -1 = 最終。例 [2, 4] = 第2・第4
  weekday: Weekday
}
```

- 第5週が存在しない月は `nth: 5` を発生させない（`-1` を使えば最終週を確実に取れる）

#### (d) `monthlyByBusinessDay` — 毎月第N営業日 / 月末からN営業日前

```ts
{
  type: "monthlyByBusinessDay",
  interval: number,
  months?: Month[],
  nth: number[]      // 正 = 月初から数えてN営業日目（1 = 第1営業日）
                     // 負 = 月末から数えてN営業日目（-1 = 最終営業日, -3 = 月末3営業日前）
}
```

- 該当月の営業日数が `|nth|` 未満なら発生させない
- **このタイプは §5.3 の営業日補正を適用しない**（定義上すでに営業日であるため）

#### (e) `fiscalRelative` — 決算月を基準にした反復

```ts
{
  type: "fiscalRelative",
  offsetMonths: number[],   // 決算月からのずれ。0=決算月, 2=2か月後, -3=3か月前
  day: number | "last"      // ずらした先の月の何日か。存在しない日は末日に丸める
}
```

決算月の末日を基準に、`offsetMonths` か月ずらした月の `day` 日に発生する。

**この型が存在する理由**は、申告期限・期首・中間申告・四半期が「暦の何月」ではなく
「決算月から何か月」で決まるためである。暦月で書くと、決算月が変わったときに
すべてのルールを直して回ることになる。決算月を営業日カレンダーの設定に持たせ、
そこを基準にすることで、**設定を1つ変えるだけで関連する予定がまとめて追従する**。

| 実務 | 表現 |
|---|---|
| 法人税・消費税の申告（事業年度終了から2か月以内） | `offsetMonths:[2] day:"last"` |
| 期首 | `offsetMonths:[1] day:1` |
| 中間申告（開始から6か月経過後2か月以内） | `offsetMonths:[8] day:"last"` |
| 四半期末 | `offsetMonths:[-9,-6,-3,0] day:"last"` |

3月決算なら申告期限は5月末、12月決算なら翌年2月末になる。営業日補正（`next`）と
組み合わせれば、期限が休業日にあたったときの繰り下げも自動で効く。

決算月は**ルールが参照する営業日カレンダー**から取る。未設定のカレンダーでは
3月として扱う（日本で最も多いため）。

> **設計メモ**: 「毎年」「四半期」「毎営業日」を独立した型にしない。
> 年次は `monthlyByDay` + `months:[m]`、四半期は `months:[3,6,9,12]` で表現できる。
> UI 側では「年次」「四半期」というプリセットボタンを用意し、内部的には上記へ変換する（糖衣構文）。

### 5.3 Adjustment（営業日補正）

```ts
type Adjustment = {
  mode: "none" | "prev" | "next" | "nearest" | "both";
  keepInMonth: boolean;   // true のとき、補正が月をまたぐ場合は逆方向へ補正する。既定 false
};
```

| mode | 挙動 |
|---|---|
| `none` | 補正しない（休業日でもその日に表示） |
| `prev` | 休業日なら**遡って**最初の営業日へ（給与振込・締め処理） |
| `next` | 休業日なら**進んで**最初の営業日へ（納付期限） |
| `nearest` | 前後で近い方の営業日へ。**距離が同じなら `prev` を優先**（前倒しの方が実務上安全） |
| `both` | 前営業日と翌営業日の**両方**へ。1つの基準日から2件の発生日が生まれる |

`both` は、同じ期日に複数の相手が絡み、相手ごとに前倒し・後ろ倒しが分かれる場合のためにある。
たとえば他社からの入金が「5の倍数と月末」に集中し、休業日のときにどちらへずれるかが
取引先によって違うケース。1つのルールで両側を押さえ、カレンダー上は `←` `→` で区別する（§8.2）。
`keepInMonth` が true のときは、当月内に収まる側だけを残す。

`keepInMonth: true` の例:
- 2026年8月1日は土曜。`mode: "prev"` なら通常は7月31日（金）だが、月をまたぐため8月3日（月）へ補正
- 月次処理を当月内に収めたい場合に使う

補正の探索は最大 **31日** まで。それを超えても営業日が見つからない場合（設定ミスで全日休業など）は
その発生日を破棄し、UI に警告を表示する。

### 5.4 Notice（事前通知 / 準備日）

```ts
type Notice = {
  offset: number;                 // 負の値のみ。-3 = 3日前
  unit: "business" | "calendar";  // 営業日換算 / 暦日換算
  label: string;                  // 例 "振込データ作成"
};
```

- 起点は**確定日**（補正後の日付）
- `unit: "business"` の場合、休業日をスキップして数える
- 表示は本体ルールと視覚的に区別する（淡色・破線枠）

### 5.5 スキーマ例

```jsonc
{
  "id": "8f1c…",
  "title": "給与振込",
  "color": "blue",
  "enabled": true,
  "calendarId": "bank",
  "recurrence": { "type": "monthlyByDay", "interval": 1, "days": [25], "overflow": "clamp" },
  "adjust": { "mode": "prev", "keepInMonth": false },
  "notices": [{ "offset": -3, "unit": "business", "label": "振込データ作成" }],
  "period": { "start": "2026-04-01", "end": null },
  "skipDates": []
}
```

## 6. 実務ユースケース対応表

仕様が「痒いところに手が届く」ことの検証。以下はすべて **1ルール** で表現できる。

| # | 実務上の決まりごと | 表現 |
|---|---|---|
| 1 | 給与振込：毎月25日、休日なら**前**営業日 | `monthlyByDay days:[25]` + `adjust:prev` |
| 2 | 月次締め：**月末営業日** | `monthlyByDay days:["last"]` + `adjust:prev` |
| 3 | 源泉所得税納付：毎月10日、休日なら**翌**営業日 | `monthlyByDay days:[10]` + `adjust:next` |
| 4 | 社会保険料引落：毎月末日、休日なら**翌**営業日 | `monthlyByDay days:["last"]` + `adjust:next` |
| 5 | 請求書発行：毎月**第5営業日** | `monthlyByBusinessDay nth:[5]` |
| 6 | 支払処理：**月末2営業日前** | `monthlyByBusinessDay nth:[-2]` |
| 7 | 定例会議：**第2・第4火曜** | `monthlyByWeekday nth:[2,4] weekday:2` |
| 8 | 部会：**毎月最終金曜** | `monthlyByWeekday nth:[-1] weekday:5` |
| 9 | 週次報告：毎週金曜、休日なら前営業日 | `weekly weekdays:[5]` + `adjust:prev` |
| 10 | 1on1：**隔週月曜** | `weekly interval:2 weekdays:[1] anchor:"2026-04-06"` |
| 11 | 四半期報告：**3/6/9/12月の月末営業日** | `monthlyByDay months:[3,6,9,12] days:["last"]` + `adjust:prev` |
| 12 | 期首棚卸：毎年4月1日、休日なら翌営業日 | `monthlyByDay months:[4] days:[1]` + `adjust:next` |
| 13 | 給与＋支払を同一ルールで：毎月10日と25日 | `monthlyByDay days:[10,25]` + `adjust:prev` |
| 14 | 決算：3月末営業日の**3営業日前から準備** | #11 に `notices:[{offset:-3, unit:"business"}]` |

| 17 | 他社入金：5の倍数と月末、相手により前倒し・後ろ倒しが分かれる | `monthlyByDay days:[5,10,15,20,25,"last"]` + `adjust:both` |

## 7. 展開アルゴリズム

### 7.1 全体フロー

```
expandRules(rules, calendars, holidays, viewRange) -> Occurrence[]

for each rule where enabled:
  1. 反復条件を viewRange（＋前後1か月のマージン）で展開 → 基準日リスト
  2. period.start / period.end で絞り込み
  3. skipDates に含まれる基準日を除外
  4. 各基準日に営業日補正を適用 → 確定日
     （monthlyByBusinessDay は補正をスキップ）
  5. 同一ルール内で確定日が重複したものを1件に統合
  6. notices を展開して副次的な Occurrence を生成
  7. viewRange 外を切り落とす
```

**マージンが必要な理由**: 月末の `prev` 補正で前月へ、月初の `next` 補正で翌月へ移動しうるため、
表示範囲の前後1か月を展開してから切り落とす。

### 7.2 Occurrence

```ts
type Occurrence = {
  ruleId: string;
  kind: "main" | "notice";
  rawDate: DateStr;        // 補正前の基準日
  date: DateStr;           // 補正後の確定日
  shifted: boolean;        // rawDate !== date
  shiftDirection: "prev" | "next" | null;
  noticeLabel?: string;
};
```

`shifted === true` の場合、UI に補正マーク（⟳）と元日付を表示する。

### 7.3 日付演算の実装方針（重要）

**タイムゾーンによるオフバイワンを構造的に防ぐ。**

- アプリの日付は常に `"YYYY-MM-DD"` 文字列で保持する
- 内部演算は `Date.UTC(y, m-1, d)` で生成した Date（＝UTC 00:00）で行い、
  取り出しは必ず `getUTCFullYear` / `getUTCMonth` / `getUTCDate` を使う
- `new Date("2026-01-01")` や `getDate()`（ローカル時刻系）は **使用禁止**。
  `tests/dateApiGuard.test.ts` が `src/` を走査して混入を検出する（`dateUtil.ts` のみ例外）。
  ESLint を導入していないのは、この1点のためだけに依存を増やす必要がないため
- 「今日」の判定のみ、`Asia/Tokyo` に固定して算出する（`Intl.DateTimeFormat` の `timeZone: "Asia/Tokyo"`）

## 8. UI 仕様

### 8.1 画面構成

```
┌───────────────────────────────────────────────────┐
│ [<] 2026年9月 [>] [今日]      [ルール] [◐] [⚙] [?] │
├───────────────────────────────────────────────────┤
│                                                   │
│                  月カレンダー（全幅）                │
│                                                   │
└───────────────────────────────────────────────────┘
```

**カレンダーは常に全幅**とし、それ以外の画面（ルール一覧・ルール編集・日付の詳細・
設定・ヘルプ）はすべて `<dialog>` のモーダルに載せる。

理由は2つ。
1. 横にパネルを置くとセル幅が削られ、予定名が折り返しやすくなる。カレンダーは
   1日の中身が読めることが最優先である
2. 1カラムに折り返す狭い画面では、パネルがカレンダーのはるか下に置かれて
   見つけにくかった。モーダルなら画面幅によらず同じ場所に出る

`<dialog>` を使うことで、Esc で閉じる・背面を操作させない・フォーカスを閉じ込める、
といった挙動をブラウザに任せられる。背景クリックでも閉じる。
なお `showModal()` は文書に接続済みの要素にしか使えないため、挿入してから開く。

ヘッダーは **左（今日）／中央（‹ 年月 ›）／右（操作）の3ゾーン**に分ける。
左右を同じ幅にすることで、年月がページ＝カレンダーの中央線に揃う。移動ボタンは
年月のすぐ両横に置き、視線の移動を小さくする。

右のボタンは順に、表示切替（カレンダー／一覧）、ルール一覧、配色モード
（◐ 自動 / ☀ ライト / ☾ ダーク）、設定（⚙）、ヘルプ（?）。
ルール・設定・ヘルプはトグルで、同じボタンをもう一度押せば閉じる。

**年月をクリックすると月の移動が開く**（§8.7）。前後1か月ずつの ‹ › だけでは
離れた月に届かないため。

**スマートフォンでは横スワイプで月を送る。** 左へ払うと次の月、右へ払うと前の月
（紙をめくる向きに合わせる）。縦スクロールを邪魔しないよう、横の移動量が縦の1.5倍を
超え、かつ60px以上動いたときだけ反応する。スワイプ直後のタップ扱いの click は
1回だけ握り潰す。そうしないと日付の詳細が同時に開いてしまう。

ルールが1件も無いときは、カレンダーの下に「サンプルを読み込む／ルールを追加」の
導線を出す。カレンダーだけでは何も始められないため。

### 8.2 月カレンダーのセル

| 要素 | 内容 |
|---|---|
| 日付 | 平日=標準色 / 土=青 / 日・祝=赤 / 休業日=グレー背景 |
| 祝日名 | 祝日の場合に小さく表示（例「敬老の日」） |
| 休業ラベル | `closedRanges` に該当する場合その label（例「年末年始休業」） |
| 予定チップ | ルールの色＋タイトル（省略しない）。補正済みなら向きと元の日を示す記号を付す |
| 事前通知チップ | 破線枠でルール色を継承 |
| 今日 | 枠を強調 |
| 選択中の日 | 枠と淡い背景で強調 |
| ホバー | セル全体がクリック可能であることを背景色で示す |

補正済みチップの記号は `←10` `→10` の形にする。`←` は前倒し、`→` は後ろ倒し、
数字は補正前の日。向きと由来の両方を2〜3文字で示せるため、`⟳` だけを出すより情報量が多く、
`both` で前後に分かれた2件を並べたときにどちらがどちらか一目で分かる。

祝日名と休業ラベルが両方該当する日（元日と年末年始休業が重なる 1/1 など）は、
**祝日名を優先して表示する**。休業していること自体は背景色が示しており、
そこに「年末年始休業」とだけ出すと「元日」という情報が失われるため。

予定チップにホバーすると、補正前の日付・補正方向・備考をツールチップ表示する。

**チップは件数でも文字数でも省略しない。** 予定名は全文を折り返し、セルは中身に
合わせて縦に伸ばす。件数の上限も設けない。反復ルールから導く性質上、1日に極端な
件数が並ぶことは考えにくく、省略するよりページをスクロールさせるほうが実務では読みやすい。

> **実装上の注意**: 以前は `-webkit-line-clamp` で2行に制限していたが、標準プロパティ
> `line-clamp` を部分実装したブラウザ（Android Chrome で確認）では
> **省略記号は出るのに溢れた行が切り取られず、セルの外へはみ出した**。
> clamp に頼らず、折り返しとセルの伸長で対処する。

**セルのどこをクリックしても**その日の詳細をモーダルで開く。日付の数字だけを
当たり判定にすると、特にスマートフォンでは狙いにくいため。

- 日付の数字は `<button>` のままにしておき、キーボードとスクリーンリーダーからの
  入口として残す。button の click はセルへ伝播するので、ハンドラはセル側に1つだけ
  置いて二重発火を避ける
- 予定名をドラッグで選択しただけのときは開かない（選択範囲があれば無視する）

### 8.3 一覧表示

今日から N 日分（30 / 90 / 180 / 365 から選択、既定 90）の発生日を時系列で列挙する。
カレンダーが「今月の形」を見るためのものなのに対し、こちらは「これから何が来るか」を
追うためのもの。印刷して配る用途も想定する。

列は `日付 / 曜日 / 予定 / 補正 / 内容`。

- 日付と曜日は、その日の**最初の行にだけ**出す。同じ日の予定がひとかたまりに見え、
  日付が変わる位置が目で追える
- 曜日は日・祝を赤、土を青にし、祝日名を添える
- 補正列には `←25` `→25`。事前通知の行には「2026-09-25 の準備」と由来を出す
- 今日の行は背景で強調する
- 日付をクリックすると日付の詳細、予定名をクリックするとそのルールの編集を開く

表示（カレンダー／一覧）と先読み日数は設定として保存する。

### 8.4 ルール編集フォーム

- 反復条件は「毎月N日 / 第N営業日 / 第N曜日 / 毎週」のタブで切替。
  種類を切り替えても、それぞれの入力内容は下書きとして保持する
- 日と対象月は 1〜31／1〜12 のトグルボタン群で選ぶ。複数選択がそのまま
  「毎月10日と25日」「3・6・9・12月」になり、入力と結果の対応が明快になる
- 「四半期」「半期」「毎月」はプリセットボタンとして提示し、内部的に `months` へ変換。
  対象月を1つだけ選べば年次になる
- 条件付きの入力欄（隔週の基準日、2月に無い日の扱い、当月内補正）は、
  関係するときだけ出す。設問が減るほど迷いが減る
- **フォーム下部に「次の10回」プレビューを常時表示**
  → 補正の効き方をその場で確認できるようにする。誤設定を最も効果的に防ぐ。
  補正された回は元の日付と方向（⟳ 2026-12-31 から前倒し）も併記する
- 保存前にバリデーション（§10.2）。エラーがある間はプレビューを出さず、
  何を直せばよいかだけを示す

### 8.5 日付の詳細

日付をクリックするとモーダルで開く。

- 日付・曜日・その日が営業日か休業日か（休業なら理由）
- その日の予定を全件（チップの上限に関係なく）。補正されたものは
  「本来は 2026-10-10（休業日）。前営業日へ前倒し。」のように由来を文章で示す
- 各項目から該当ルールの編集へ移動できる
- 前日／翌日ボタンで日を送る。月をまたぐ場合は表示月も追従する

### 8.6 ヘルプ

「反復ルール」と「営業日補正」はこのアプリ固有の概念のため、画面内に説明を置く。
繰り返しの種類、補正の種類（`both` を含む）、カレンダーの記号、営業日カレンダー、
データの保存先とバックアップ方法を扱う。

### 8.7 月の移動

年月をクリックすると開く。年を ‹ › で送り、12か月のボタンから選ぶ。
今日が属する月には印を付け、いま何月から離れているかの手がかりにする。
「今日の月へ」で一度に戻れる。

### 8.8 配色モード

`auto`（OS の設定に従う）/ `light` / `dark` の3状態を巡回で切り替える。
選択は設定として保存し、次回起動時にも適用する。

CSS では light のトークンを `:root` に置き、dark を
`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` と
`:root[data-theme="dark"]` の両方に定義する。これにより、OS がダークでも
明示的に light を選べば上書きできる。

### 8.9 印刷

カレンダー・一覧のどちらも、そのまま印刷して配れる状態にする。

- 用紙では**常に白地・黒文字**にする。配色トークンのダーク定義は `:root` より
  詳細度が高いセレクタに置いてあるため、印刷時の上書きも**同じセレクタを並べて**
  行う。素の `:root` だけに書くと詳細度で負け、ダークモードのまま印刷したときに
  文字が薄いまま残る（実際に一度その状態になった。`tests/printCss.test.ts` が
  構造を検査する）
- 操作用の要素（ヘッダー・モーダル・バナー・凡例・リンク）は印刷しない
- 画面ではヘッダーが月やレンジを示しているが紙には残らないため、
  印刷時だけ見出し（`2026年9月` / `2026-09-05 〜 2026-12-03 の予定`）を出す
- 営業日数と祝日データの出典は、紙に残る情報として意味があるので印刷する
- 今日の枠は色ではなく太線で示す。単色印刷でも分かるようにするため
- 予定チップは塗りではなく枠線にする（インク節約と可読性）
- 週の行・一覧の行が用紙をまたいで割れないようにする（`break-inside: avoid`）

### 8.10 アプリ名と版

画面上部にアプリ名（営業日スケジュール）と版（`v1.0.0`）を常に出す。
静的サイトは「いま見ているものがいつのものか」が分かりにくく、不具合の報告を
受けたときに版を突き合わせられないと原因を追えないため。

版・ビルド日時・コミットはビルド時に埋め込む（`vite.config.ts` の `define`）。
設定の「このアプリについて」に詳細を、フッターと印刷にも版を出す。

### 8.11 アクセシビリティ

- **ランドマーク**: `header` / `main` / `footer` を分ける。冒頭に「本文へ移動」の
  スキップリンクを置く
- **フォーム**: 入力欄が1つに定まる `field` は `label`/`for` で結ぶ。トグル群は
  `role="group"` と `aria-labelledby`。説明は `aria-describedby`。
  1つの枠に複数の入力欄が並ぶ場合（期間の開始・終了など）は欄ごとに `aria-label` を付ける
  - ただし**ボタンにロールをかぶせない**。`role="group"` を付けるとボタンでなくなる
    （実際にこれで書き出しボタンが押せなくなった）
- **カレンダーのキーボード操作**: 42個のボタンを全部タブ順に入れると通り抜けるだけで
  大変になるため、代表の1つだけを `tabindex="0"` にし（roving tabindex）、
  矢印キー・Home/End・Page Up/Down で移動する。月をまたぐ移動では、描き直したあとに
  同じ日へフォーカスを戻す
- **通知**: バナーと検証結果は `role="status"` の live region に置く
- **コントラスト**: 淡色は AA を満たす値にする。
  前後の月のセルを**透明度で薄くしない**。文字のコントラストが落ちて読めなくなるため、
  背景と日付の色で区別する（実際に AA を満たしていなかった）

`axe-core` を E2E に組み込み、主要画面（カレンダー・一覧・ルール編集・設定・ヘルプ）で
違反ゼロを保つ。

### 8.12 設定画面

- 営業日カレンダーの編集（週末曜日、祝日を使うか、**決算月**、休業期間、臨時休業日、臨時営業日）
  - 変更するとその場で「今月の営業日は N 日です」を更新し、左のカレンダーも描き直す。
    設定の影響を数字と実物の双方で確かめられるようにするため
- 祝日データの出典・取得日時・収録範囲・二次検証の結果を表示
- JSON エクスポート／インポート（置き換え／マージ）
- 全データ削除

## 9. 永続化とデータ入出力

### 9.1 保存先

`localStorage` を正とする。サーバー・認証なし。

| キー | 内容 |
|---|---|
| `bds.v1.rules` | `Rule[]` |
| `bds.v1.calendars` | `BusinessCalendar[]` |
| `bds.v1.prefs` | 表示設定（既定ビュー、一覧の日数、配色モード） |
| `bds.v1.schemaVersion` | スキーマ版数。マイグレーションの起点 |

`localStorage` が使えない環境（プライベートモード等）では、メモリ上で動作しつつ
「この端末には保存されません」と警告バナーを出す。

### 9.2 エクスポート／インポート

単一 JSON ファイル `business-days-schedule-YYYYMMDD.json`:

```jsonc
{
  "schemaVersion": 1,
  "exportedAt": "2026-09-04T10:00:00+09:00",
  "calendars": [ /* BusinessCalendar[] */ ],
  "rules": [ /* Rule[] */ ],
  "prefs": { }
}
```

- インポート時は「置換」「マージ（ID 重複は取り込み側を採用）」を選択
- スキーマ検証に失敗したファイルは取り込まず、エラー箇所を明示
- 端末間の移行・バックアップ・バージョン管理（このファイル自体を Git 管理する）に使う

### 9.3 サンプル定義の同梱

`public/data/samples/` に、種類ごとに分けたサンプルの束を置く。
`index.json` が束の一覧（id・名前・説明・ファイル・件数）を持ち、UI はこれを読んで並べる。

| 束 | 内容 |
|---|---|
| `business-basics` | 給与振込・月次締め・請求書発行・支払処理・定例会議 |
| `tax` | 源泉所得税、住民税、社会保険、年度更新、算定基礎届、法定調書、償却資産申告。申告期限・期首・中間申告・四半期は `fiscalRelative` で決算月に追従する |
| `receivables` | 締め日、請求書発行、入金予定（`both`）、入金消込、督促 |
| `payables` | 仕入請求書の受領、支払データ作成、買掛金振込、給与、賞与、経費精算 |
| `meetings` | 週次報告、月次定例、経営会議、四半期報告、隔週1on1 |

- **使い始めたあとでも追加できる。** ルール一覧に「サンプル」ボタンを常設する。
  新規ルールの追加とはボタンを分ける（目的が違うため）。
  空のときにしか導線を出していなかったころは、使い始めると到達できなくなっていた
- 追加は**マージ**なので既存のルールは消えない。同じ束を再度追加すると、
  その束のルールだけが元の内容へ戻る（ID が束ごとに固定されているため）
- **束は `calendars` を持たない。** 追加のたびに利用者の営業日設定を上書きしてしまうため、
  空配列にしてある（マージ時に現在の設定がそのまま残る）
- 日付や名称は目安であり、正確性より「型として使えること」を優先する。
  その旨を画面に明記する

### 9.4 外部カレンダーへの書き出し

Google カレンダーや Outlook など、会社指定のカレンダーへ取り込むための書き出し。

**反復ルールそのものは渡さない。** 営業日補正は相手のカレンダーでは再現できないため、
指定期間の発生日へ展開し、確定済みの日付を持つ単発の予定として渡す。
期間の指定が必須なのはこのため。期間が過ぎたら書き出し直す。

| 形式 | 用途 |
|---|---|
| **iCalendar (.ics)** | 既定。Google・Outlook・Apple のいずれでも読める |
| **CSV** | Google カレンダーの取り込みと、表計算で中身を確かめたいとき |

CSV を既定にしないのは、Outlook.com がカレンダーの CSV 取り込みに対応していないため。

実装上の要点:

- 終日予定として出す。iCalendar の `DTEND` は排他的なので**翌日**を指定する
- `UID` は `ルールID-種別-日付@business-days-schedule` の形にする。内容から決まるため、
  同じ期間を書き出し直して取り込んでも重複ではなく更新として扱われる
- iCalendar は1行75**オクテット**で折り返す（RFC 5545 §3.1）。日本語は1文字3オクテットに
  なるため、文字数で数えると規格違反になる。マルチバイト文字の途中では折らない
- 改行は CRLF。`,` `;` `\` と改行はエスケープする
- **補正の由来を `DESCRIPTION` に残す**（「本来は 2026-10-25（休業日）。前営業日へ前倒し。」）。
  取り込んだ先で日付だけ見ても理由が分からなくなるのを防ぐ
- CSV には BOM を付ける。表計算ソフトで開いたときの文字化けを防ぐためで、
  Google カレンダーの取り込みは BOM 付きでも読める

## 10. 品質・エッジケース

### 10.1 テスト観点（Vitest / Playwright）

単体テスト（Vitest）に加えて、**保存と画面をまたぐ流れは E2E（Playwright）**で確かめる。
「編集 → 再読込 → 再追加」のような順序依存の不具合は単体テストの構造では拾えず、
実際にサンプル再追加で編集内容が失われる不具合を取り逃がしていた。

E2E は本番ビルド（`dist/`）を素の静的配信で動かす（`scripts/serve-dist.ts`）。
GitHub Pages と同じ条件に近づけ、公開後にだけ壊れる不具合を拾うため。
デスクトップ幅とスマートフォン幅の2構成で実行する。


| 領域 | ケース |
|---|---|
| 営業日判定 | `openDates` が祝日・週末より優先されること／`closedRanges` の年跨ぎ（12-29〜01-03） |
| monthlyByDay | 31日指定 × 2月（clamp / skip）／うるう年 2/29／`"last"` の各月 |
| monthlyByWeekday | 第5週が無い月／`nth: -1` と `nth: 5` が一致する月・しない月 |
| monthlyByBusinessDay | 営業日数が不足する月／`-1` が月末営業日と一致すること |
| weekly | `interval: 2` の位相が `anchor` 起点で正しいこと／年跨ぎで位相がずれないこと |
| 補正 | `prev`/`next`/`nearest`（同距離は prev）／`both` が前後2件を返すこと／`keepInMonth` の反転と `both` での片側除外／連続休業（GW・年末年始）の跨ぎ |
| 通知 | `unit: "business"` が休業日をスキップすること |
| 境界 | 表示範囲の端で補正により入退場する発生日／`period` 境界 |
| 日付演算 | TZ を UTC / Asia/Tokyo / America/New_York に切り替えても結果が同一であること |
| I/O | 不正 JSON のインポートが拒否されること／エクスポート→インポートの往復同一性 |
| 配信データ | `public/data/holidays.json` が実在日付・昇順・今年と来年をカバーしていること |
| サンプル | 全束がそのまま取り込め、警告なしで1年分展開できること／束が `calendars` を持たないこと／ID が束をまたいで衝突しないこと／一覧とファイルが一致すること |
| 書き出し | iCalendar の折り返しが75オクテットでマルチバイトを壊さないこと／`DTEND` が翌日であること／`UID` が安定していること／CSV の列がずれないこと |
| 実務ユースケース | §6 の17件が各1ルールで意図どおりの日付になること |
| 決算月 | 決算月を変えると申告期限・期首・四半期がまとめて動くこと／年をまたぐずれ／うるう年／未設定時の既定（3月）／営業日補正との組み合わせ |
| 表示 | 休業日・祝日・補正マーク（`←10`/`→10`）がマークアップに現れること／件数と文字数のどちらも省略しないこと／ルール名の HTML がエスケープされること |
| 一覧 | 日付昇順であること／同じ日の2件目以降が日付を繰り返さないこと／補正と事前通知の由来が出ること |
| 印刷 | 印刷ブロックがダークと同じセレクタをすべて上書きすること／操作用の要素を隠し、紙に残す情報を出すこと |
| 事前通知の範囲 | 60営業日前・60暦日前・年をまたぐ通知が、通知日を含む表示で出ること |
| 壊れた入力 | 任意の値で `validateRule` / `validateCalendar` が例外を投げないこと／壊れた localStorage でも起動できること／巨大な通知日数を弾くこと |
| サンプルの取り込み | `add` が既存 ID を触らないこと／`merge` が明示操作のときだけ上書きすること |
| 月の移動 | 年をまたいで選べること／表示中の月と今日の月に印が付くこと |
| スワイプ | 横が優勢なときだけ反応すること／縦スクロールと2本指を無視すること／直後の click を1回だけ止めること |
| スタイル | `[hidden]` が `!important` で効いていること（作者スタイルの display 指定に負けないため） |
| セルの操作 | 数字・余白・予定チップのいずれをクリックしても1回だけ詳細が開くこと／文字選択中は開かないこと |
| モーダル | 文書へ挿入してから開くこと（`showModal()` の制約）／背景クリックと閉じるボタンで閉じること／中身だけ差し替えられること |
| 日付詳細 | 営業日／休業理由の表示、補正の由来、上限を超える件数でも全件出ること |
| 配色 | `data-theme` の付け外しと巡回順 |
| 文言 | ルールの日本語要約（「毎月末から2営業日前」など）が崩れないこと |
| 編集 | 入力を変えるとプレビューが即座に追従すること／不正な設定では保存できないこと／編集中に元のルールを書き換えないこと |
| 設定 | 週末曜日・臨時営業日の変更が営業日数と表示に反映されること |

祝日データはテスト用に固定スナップショットを使い、外部取得に依存させない。

### 10.2 バリデーション

`validateRule` / `validateCalendar` は**任意の値**を受け取りうる前提で書く（§13）。

- 型そのものを確かめる（文字列か、配列か、真偽値か）。欠けていれば issue にする
- `weekly` は `weekdays` が1つ以上
- `1 <= interval <= 120`
- `days` の要素は 1〜31 または `"last"`
- `period.start <= period.end`
- `notices[].offset` は `-1` 〜 `-365` の整数。
  **上限は必須**。営業日換算で巨大な値を渡されると、数えるだけで固まるため
- 件数・文字数の上限（タイトル200字、メモ2000字、通知20件、除外日1000件）
- 保存時にプレビューが0件になるルールは警告（保存自体は許可）

### 10.3 非機能

| 項目 | 目標 |
|---|---|
| 初期表示 | 3G 相当で 2 秒以内（バンドル < 150KB gzip、外部ランタイム依存なし） |
| オフライン | 祝日 JSON をキャッシュし、2回目以降はオフラインで動作（Service Worker は v2 で検討） |
| a11y | WCAG 2.1 AA（axe-core で自動検査）。キーボードだけで操作可能、コントラスト比 4.5:1 以上、色のみに依存しない情報伝達 |
| オフライン | 一度開いたあとは通信が無くても表示・操作できる |
| ブラウザ | 直近2バージョンの Chrome / Edge / Safari / Firefox |

## 13. オフライン対応

一度開いたあとは、通信が無くても表示・操作できるようにする。
外出先や電波の悪い場所で開けないと、日々の道具としては使えないため。

`scripts/build-sw.ts` がビルド後の `dist/` を走査し、事前キャッシュ一覧を埋め込んだ
`sw.js` を生成する。一覧を手で持つと、資産名のハッシュが変わるたびに更新漏れが起きる。
キャッシュ名は中身のハッシュから決めるので、内容が変われば必ず名前が変わり、
古いキャッシュが残り続けない。

| 対象 | 方針 |
|---|---|
| 画面遷移（navigate） | ネットワーク優先。オフラインのときだけキャッシュへ |
| ハッシュ付きの資産 | キャッシュ優先。URL が内容と対応しているため古いものを掴まない |
| 祝日データ・サンプル | stale-while-revalidate。すぐ出しつつ裏で更新 |

**更新は勝手に適用しない。** 新しい版を検知したら画面下に案内を出し、
利用者が「再読み込み」を選んだときだけ切り替える。編集途中のフォームを
黙って作り直さないため。

> **注意**: `clients.claim()` は**初回登録でも** `controllerchange` を起こす。
> これを更新と取り違えて読み込み直すと、初めて開いた人が必ず1回リロードされ、
> 入力途中のものも巻き込む。実際にその状態になったため、
> 「利用者が更新を選んだかどうか」を見てから読み込み直す。
> `e2e/serviceWorker.spec.ts` が回帰を検出する。

開発中は登録しない（`import.meta.env.PROD` のときだけ）。キャッシュが邪魔になるため。

## 14. 堅牢性の方針

外から来る値は、型が正しいと仮定しない。`localStorage` も取り込む JSON も
利用者が差し替えられるため、TypeScript の型は実行時には何も保証しない。

- `validateRule` / `validateCalendar` は**どんな値を渡されても例外を投げない**。
  問題は issue として返しきる。1件の破損で起動不能になってはいけない
- 読み込み時は健全なものだけを残し、捨てた件数を利用者へ知らせる
- 実務でありえない大きさには上限を置く（§10.2）。特に事前通知のさかのぼり日数は、
  営業日換算で巨大な値を渡されると数えるだけで固まるため、上限を必須とする
